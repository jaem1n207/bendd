Arc를 떠나기로 했어요. 사용 경험이 불편해져서가 아니라, 계속 쓸 수 있는 시간이 정해졌기 때문이에요. [Arc 공식 공지](https://arc.net/)에 따르면 macOS와 Windows 버전은 2026년 12월 22일에 종료돼요.

## 세로 탭만으로 채워지지 않는 것들

Arc에서 좋았던 건 세로로 놓인 탭만이 아니었어요. 한 창 안에서 업무용·개인용 탭을 나누는 Spaces, Option+클릭이나 드래그로 링크·탭을 나란히 놓는 분할 보기, 방금 보던 탭으로 돌아가는 전환 방식이 함께 작업 흐름을 만들어줬어요.

[Zen Browser](https://zen-browser.app/)라는 훌륭한 대안도 있었어요. 다만 Firefox·Gecko 기반으로 옮기며 일부 웹의 레이아웃이나 기능 호환성을 다시 신경 쓰고 싶지는 않았어요. 이번 이주에서는 익숙한 Chromium 환경을 유지하고 싶었어요.

마침 Chrome도 [세로 탭을 공식 지원](https://blog.google/products-and-platforms/products/chrome/new-chrome-productivity-features/)하기 시작했어요. 탭 목록과 그룹을 옆에 놓으니 Arc의 배치에 조금은 가까워졌어요. 하지만 제게 Arc는 Spaces, 키보드 제어, 작업 상태 복구까지 이어지는 작업 공간이었어요. 목록의 방향이 같아졌다고 같은 경험이 되지는 않았어요.

그래도 세로 탭이 생긴 건 반가웠어요. 분할 보기도 Mac에서는 [`⌘+Option+N`](https://support.google.com/chrome/answer/16971124)으로 시작할 수 있었고요. Chrome으로 돌아가되, 가장 아쉬운 탭 전환부터 직접 채워보기로 했어요.

## 가져오고 싶었던 건 손을 놓는 순간이에요

개발 문서를 읽다가 참고 자료를 확인하고 다시 돌아오는 일이 많아요. 탭의 위치를 따라 단축키를 여러 번 누르다 보면, 찾던 탭보다 옆의 탭에 먼저 도착해 흐름이 끊겼어요. Arc에서는 한 번만 눌러 직전 탭으로 돌아갈 수 있었어요.

이런 순서를 MRU(Most Recently Used), 최근 사용 순서라고 해요. 탭의 물리적 위치보다 **제가 일하던 시간의 순서**를 따라가요.

웹스토어에서 MRU 전환을 제공하는 확장 2~3개를 찾아 하나씩 써봤어요. 전환이 매끄럽지 않거나, Control을 유지하며 미리보기를 고르는 동작이 어색했어요. 자주 쓰는 전환마다 애니메이션을 기다리는 것도 답답했고요. `Ctrl+Q` 같은 다른 키를 새로 익히기보다, 손에 익은 `Ctrl+Tab`을 그대로 쓰고 싶었어요.

그래서 Chromium MRU Switcher의 목표를 세 가지로 정했어요.

- **짧게 누르면** 전환창 없이 직전 탭으로 돌아가요.
- **Control을 유지하면** 후보만 바뀌고, 뒤의 실제 페이지는 그대로 있어요.
- **Control을 놓으면** 선택을 확정하고, Esc를 누르면 취소해요.

짧게 왕복할 때는 전환창을 건너뛰고, 길게 누르면 배경 페이지를 유지한 채 후보를 고를 수 있어요. 제가 Arc에서 이어오고 싶었던 흐름이에요.

첫 버전은 현재 창의 최근 탭 다섯 개로 좁혔어요. 다른 창이나 프로필의 탭을 섞지 않고, 한 번 Control을 누르고 있는 동안에는 후보 순서를 고정했어요. 고르는 중에 순서가 바뀌면 같은 횟수의 Tab을 눌러도 도착지가 달라질 수 있으니까요.

## Ctrl+Tab을 지키려니 보조 앱이 필요했어요

가장 먼저 부딪힌 건 Chrome의 입력 경계였어요. [Commands API](https://developer.chrome.com/docs/extensions/reference/api/commands)의 지원 키에는 `Tab`이 없고, 키 해제 이벤트도 제공하지 않아요. 원하는 단축키와 확정 시점을 이 API에 맡길 수 없었어요.

웹페이지 안에서 키를 받고 전환창을 띄우는 방식도 목표와 맞지 않았어요. 주소창과 Chrome 내부 페이지까지 같은 방식으로 다룰 수 없고, 페이지의 실행 상태에 반응을 맡기게 되니까요.

| 접근                         | 선택 기준에서 걸린 부분                                 |
| ---------------------------- | ------------------------------------------------------- |
| 확장만 사용                  | 원하는 단축키와 키 해제 시점을 처리하기 어려워요        |
| 보조 앱 + 페이지 안의 UI     | 주소창·내부 페이지에서 표시 경로가 달라져요             |
| 보조 앱 + 네이티브 UI + 확장 | 설치와 권한 설정이 늘지만 입력·표시를 페이지와 분리해요 |

그래서 **Swift/AppKit 앱은 입력과 전환창을, TypeScript 기반 Manifest V3 확장은 탭 정보를 맡도록** 나눴어요. 앱은 `CGEventTap`으로 입력을 받고, Chrome의 포커스를 가져오지 않는 `NSPanel`을 띄워요. 실제 탭 활성화는 확장의 `tabs.update`가 담당해요.

전환창에 웹 문서를 올릴 필요는 없었어요. WebView나 Electron을 더하지 않고 AppKit으로 직접 그렸어요.

둘 사이는 [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)으로 연결했어요. 메시지마다 프로세스를 만드는 대신 `connectNative()`로 연결을 유지하고, 작은 Host가 사용자 전용 Unix socket을 통해 상주 앱에 전달해요. 프로필이 늘어도 입력 감시와 전환창이 중복되지 않는 구조예요.

대신 사용자는 확장과 보조 앱을 함께 설치하고 macOS 접근성 권한을 허용해야 해요. 설치 단계를 늘리는 비용을 감수하고, 본문과 주소창에서 같은 조작을 이어가는 쪽을 택했어요.

## Chrome의 응답보다 다음 입력이 먼저 왔어요

빠른 왕복에서는 `A → B` 요청이 끝나기 전에 다시 A로 돌아가라는 입력이 들어와요. Chrome의 응답을 기다린 뒤에만 MRU를 갱신하면 다음 입력이 오래된 순서를 보게 돼요. 반대로 모든 요청을 쌓으면 손을 멈춘 뒤에도 탭이 뒤늦게 바뀔 수 있고요.

그래서 **입력이 뜻하는 상태와 Chrome이 확인한 상태를 분리**했어요. Control을 놓으면 논리적 MRU를 먼저 갱신해 다음 입력의 기준으로 삼아요. 실제 활성화는 한 번에 하나만 보내고, 기다리는 동안에는 가장 최근의 목적지만 남겨요.

응답에는 연결 세대와 요청 순번을 붙여 현재 요청과 대조했어요. 재연결 이전의 응답이 새 선택을 덮어쓰지 않도록요. 확장에서도 활성화 직전에 대상 탭과 현재 창을 확인하고, 다른 창이나 앱으로 이동하면 진행 중인 선택을 취소해요.

## 기다릴 것은 전환창이고, 탭 전환은 아니었어요

실제 키보드로 빠르게 왕복해보니 짧은 입력에서도 전환창이 번쩍였어요. 처음에는 표시 대기를 120ms에서 300ms로 늘렸어요. 깜빡임을 피한 뒤에는 길게 눌렀을 때의 반응도 다시 맞춰야 했어요.

이후 설치된 Arc의 표시 예약 코드를 정적으로 분석해 100ms 기준을 확인했고, 첫 입력부터 경과한 시간을 빼서 남은 시간만 기다리도록 바꿨어요. 현재는 첫 입력의 100ms 뒤를 기준으로 표시를 예약하고, 두 번째 Tab을 누르면 대기 없이 후보를 보여줘요. 정적 분석값을 참고한 것이며 Arc와 프레임 단위로 같다는 뜻은 아니에요.

여기서 분리해야 했던 건 **표시 대기와 전환 요청**이었어요. Control을 놓으면 표시 타이머와 상관없이 즉시 활성화를 요청해요. 이미 끝난 입력의 타이머가 늦게 전환창을 띄우지 못하도록 제스처 식별자도 검사해요.

전환 지연은 별도로 계측했어요. 재측정에서 느린 입력 하나를 나눠보니 네이티브 처리보다 Chrome API 왕복이 대부분을 차지했어요. 활성화 경로에는 포커스 조회가 두 번 있었고요. 앞의 조회는 뒤따르는 비동기 작업 이후의 상태를 보장하지 못했어요. 대상 탭 검사 뒤의 마지막 포커스 확인을 유지하고, 중복 조회 한 번을 제거했어요.

| Control 해제 → Chrome API 응답 | 변경 전 | 변경 후 |
| ------------------------------ | ------: | ------: |
| 중앙값                         |  24.2ms |  20.8ms |
| p95                            | 140.3ms |  59.7ms |

같은 Mac에서 약 초당 4~5회 입력하며 기록한 응답 75개와 129개를 비교했어요. 일부 응답 기록이 빠졌고 부하도 달라, 차이 전체를 코드 수정 효과로 볼 수는 없어요. 확실한 변화는 API 왕복을 네 번에서 세 번으로 줄인 것이에요.

이 수치는 화면이 다 그려진 시간이 아니에요. 초기 목표였던 p95 50ms에도 아직 못 미쳤고, 앞서 관찰한 987ms 지연 한 건은 당시 호출별 기록이 없어 원인을 확정하지 못했어요.

## 미리보기는 풍부함보다 정확성이 먼저였어요

배경 탭의 화면을 얻으려고 그 탭을 잠깐 활성화하면, 미리보기를 만드는 과정이 사용자의 탭 전환을 방해해요. 그래서 현재 보이는 탭을 비동기로 캡처해두고, 전환창에서는 마지막으로 확보한 이미지를 보여주기로 했어요.

문제는 캡처를 시작한 탭과 결과를 받을 때의 탭이 다를 수 있다는 점이에요. A를 캡처하는 사이 B로 이동했다면, 늦게 온 이미지를 B의 미리보기로 붙여서는 안 돼요.

캡처와 축소 전후의 상태를 확인하고, 이미지 키에도 연결·창·탭·탐색 세대를 넣었어요. 상태가 달라졌으면 결과를 버려요. 캡처가 없거나 제한된 페이지는 제목과 아이콘만 보여주고요. 실시간 화면을 약속하는 대신, 다른 탭의 이미지를 보여주지 않는 쪽을 택했어요.

## 손에 익은 동작을 남기며 배운 것

현재 Mac에서는 빠른 왕복, 후보 탐색과 취소, 주소창·전체화면, 탭 이동·삭제, 연결 복구, 세 화면에서의 표시를 확인했어요. 다만 다른 Mac의 최초 설치와 일부 권한·연결 경합은 검증이 남아 있어요. 현재 지원 범위도 macOS와 Chrome이며, 일반 사용자 배포 전 단계예요.

보조 앱이 생기면서 복구도 제품의 동작이 됐어요. 개발용 서명이 바뀌면 접근성 권한을 다시 등록해야 했고, 앱을 종료했는데 Host가 다시 실행하는 버그도 만났어요. 명시적 종료 상태를 저장해 자동 실행을 막고, 사용자가 앱을 직접 열면 해제하도록 고쳤어요.

처음에는 작은 탭 전환 기능이라고 생각했어요. 만들고 보니 키를 누르는 순간, 후보를 고르는 동안, 손을 놓은 뒤의 응답까지 하나의 경험이었어요. **익숙한 조작을 옮기려면 화면뿐 아니라 입력과 상태의 경계도 함께 설계해야 했어요.** 이 프로젝트에서 가장 오래 남은 기준이에요.
