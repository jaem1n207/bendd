브라우저 확장과 네이티브 앱의 역할을 어떻게 나눴는지, 연속 입력보다 늦게 도착하는 응답을 어떻게 처리했는지 정리했어요. 키보드 중심 기능을 구현하거나, 응답을 기다리는 동안에도 다음 입력을 받아야 하는 UI를 설계할 때 참고할 수 있어요.

## Chrome으로 돌아가기로 한 이유

Arc를 떠나기로 한 계기는 [공식 지원 종료 공지](https://arc.net/)였어요. macOS와 Windows 버전은 2026년 12월 22일에 종료될 예정이에요.

Arc에서는 한 창 안에서도 Spaces로 업무용·개인용 작업을 나눌 수 있었어요. Option+클릭이나 드래그로 페이지를 나란히 놓는 분할 보기도 편했고요. 개발 문서와 작업 화면을 오갈 때는 직전에 보던 탭으로 한 번에 돌아가는 전환 기능을 특히 자주 썼어요.

[Zen Browser](https://zen-browser.app/)도 대안이었어요. 다만 Firefox의 Gecko 엔진을 기반으로 만든 브라우저라, 일부 웹에서 레이아웃이 깨지거나 기능이 동작하지 않는 호환성 문제를 겪게 될까 걱정됐어요. 그래서 익숙한 Chromium 기반의 Chrome으로 돌아가기로 했어요.

마침 Chrome도 [세로 탭을 공식 지원](https://blog.google/products-and-platforms/products/chrome/new-chrome-productivity-features/)하기 시작했어요. 써보니 탭 목록과 그룹을 옆에 놓는 기능에 가까웠어요. Spaces로 작업 환경을 나누고, 키보드로 제어하고, 작업 상태를 복구하던 Arc와는 차이가 있었어요.

그래도 세로 탭이 생긴 건 반가웠어요. 분할 보기도 Mac에서는 [`⌘+Option+N`](https://support.google.com/chrome/answer/16971124)으로 시작할 수 있었고요. 나머지는 적응하더라도, 자주 쓰던 탭 전환만큼은 같은 방식으로 쓰고 싶었어요.

## 최근에 본 탭으로 바로 돌아가고 싶었어요

개발 문서를 읽다가 참고 자료를 확인하고 다시 돌아오는 일이 많아요. Chrome에서는 탭이 놓인 위치를 따라 단축키를 여러 번 눌러야 했어요. 방금 보던 탭인데도 다시 찾아가야 했죠.

Arc는 **최근에 본 탭(MRU)** 순서로 이동해요. 탭을 어디에 열어뒀는지 기억하지 않아도 직전 작업으로 돌아갈 수 있어서, 여러 탭을 오갈 때 맥락을 유지하기 좋았어요.

웹스토어에서 MRU 방식으로 전환하는 확장 2~3개를 찾아 써봤어요. 전환 자체가 매끄럽지 않거나, Control을 누른 채 Tab으로 후보를 고르고 Control을 놓아 확정하는 동작이 어색했어요.

전환창이 열리고 닫힐 때마다 재생되는 애니메이션도 답답했어요. 탭을 수시로 오가다 보니, 매번 효과가 끝나기를 기다리는 느낌이 들었거든요. 자주 쓰는 조작일수록 애니메이션을 줄이거나 생략하고, 입력에 바로 반응해야 한다고 생각했어요.

`Ctrl+Q` 같은 새 단축키를 익히기보다는 손에 익은 `Ctrl+Tab`을 그대로 쓰고 싶었어요. 이렇게 만든 프로그램이 Chromium MRU Switcher예요. 목표로 삼은 동작은 세 가지였어요.

- **짧게 눌렀다 놓으면** 전환창 없이 직전 탭으로 돌아가요.
- **길게 누르면** 전환창이 열려요. Control을 누른 채 Tab으로 후보를 고르는 동안, 뒤의 실제 페이지는 바뀌지 않아요.
- **Control을 놓으면** 선택한 탭으로 전환하고, Esc를 누르면 취소해요.

후보는 현재 창의 최근 탭 다섯 개로 제한했어요. 다른 창이나 프로필의 탭은 섞지 않고, Control을 누른 동안에는 목록 순서를 고정했어요. 탭을 고르는 도중 순서가 바뀌면 같은 횟수로 Tab을 눌러도 다른 탭에 도착할 수 있으니까요.

## 익숙한 단축키를 쓰려면 보조 앱이 필요했어요

최근 탭을 찾고 활성화하는 일은 확장으로 할 수 있었어요. 문제는 `Ctrl+Tab`을 누르고 놓는 동작이었어요. Chrome의 [Commands API](https://developer.chrome.com/docs/extensions/reference/api/commands)는 단축키로 `Tab`을 지원하지 않고, 키를 놓는 이벤트도 제공하지 않아요.

웹페이지 안에서 키 입력을 받고 전환창을 띄우는 방식도 생각했어요. 하지만 주소창이나 Chrome 내부 페이지에서는 같은 방식으로 동작하게 만들기 어려웠어요. 어느 페이지를 보고 있든 익숙한 단축키 하나로 전환하려면 입력과 전환창을 웹페이지 밖에서 처리해야 했어요.

| 방식                         | 감수해야 하는 제약                                      |
| ---------------------------- | ------------------------------------------------------- |
| 확장만 사용                  | 원하는 단축키와 Control 해제 시점을 처리하기 어려워요    |
| 보조 앱 + 페이지 안의 전환창 | 주소창·Chrome 내부 페이지에서 같은 전환창을 쓰기 어려워요 |
| 보조 앱 + 네이티브 전환창 + 확장 | 보조 앱 설치와 macOS 권한 설정이 추가돼요              |

그래서 **Swift/AppKit 앱은 키 입력과 전환창을, TypeScript로 쓴 Manifest V3 확장은 탭 정보와 활성화를 맡도록** 나눴어요. 앱은 `CGEventTap`으로 입력을 받고, Chrome의 포커스를 가져오지 않는 `NSPanel`로 후보를 보여줘요. 선택한 탭은 확장이 `tabs.update`로 활성화해요. 간단한 탭 카드 UI라 별도의 웹 런타임을 더하지 않고 AppKit으로 직접 그렸어요.

확장과 앱 사이는 [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)으로 연결했어요. 확장은 `connectNative()`로 작은 중계 프로세스인 Native Host와 연결을 유지하고, Host는 사용자 전용 Unix socket으로 상주 앱에 메시지를 전달해요. 프로필이 늘어도 키 입력을 감시하는 앱과 전환창이 중복되지 않게 했어요.

사용자는 확장과 앱을 함께 설치하고 macOS 접근성 권한도 허용해야 해요. 설치 단계가 늘더라도 본문과 주소창에서 같은 조작을 쓸 수 있게 하는 쪽을 선택했어요.

## 짧은 입력에는 전환창을 띄우지 않았어요

실제 키보드로 빠르게 왕복해보니 짧은 입력에서도 전환창이 번쩍였어요. 처음에는 표시 대기를 120ms에서 300ms로 늘렸어요. 하지만 대기를 길게 잡으면 탭을 고르려고 길게 눌렀을 때도 창이 늦게 열려요.

이후 설치된 Arc의 표시 예약 코드를 정적으로 분석해 확인한 100ms를 참고했어요. 지금은 첫 입력의 100ms 뒤에 전환창이 열리도록 예약하고, 두 번째 Tab을 누르면 기다리지 않고 보여줘요. 첫 입력부터 이미 지난 시간을 빼고 남은 시간만 기다리도록 했고요.

반대로 Control을 먼저 놓으면 표시 예약을 취소하고 바로 탭 활성화를 요청해요. **전환창을 보여주기 위한 대기가 실제 탭 전환까지 늦추지 않도록** 분리했어요. 이미 끝난 조작의 타이머가 뒤늦게 창을 띄우지 못하게 조작마다 식별자를 붙였고, Control을 놓거나 Esc를 누르면 창도 바로 닫게 했어요.

## 탭 전환 응답이 오기 전에 다음 입력이 들어왔어요

문서 A와 참고 자료 B를 빠르게 오갈 때는 다른 문제가 생겼어요. B로 전환하라는 요청을 보냈는데, Chrome의 활성화 완료 응답이 오기 전에 다시 A로 돌아가라는 입력이 들어오는 거예요.

응답을 받은 뒤에만 최근 탭 순서를 바꾸면 두 번째 입력도 A를 기준으로 해석해서 B를 고르게 돼요. 그렇다고 모든 전환 요청을 쌓아두면 키를 놓은 뒤에도 탭이 뒤늦게 바뀔 수 있고요.

그래서 **다음 입력의 기준이 되는 탭 순서와 Chrome에서 확인한 상태를 따로 관리**했어요. Control을 놓으면 선택한 탭을 최근 순서의 맨 앞으로 옮겨 다음 입력에 반영해요. 실제 전환 요청은 한 번에 하나만 보내고, 처리 중에 들어온 선택은 마지막 목적지만 남겨요.

오래된 연결에서 온 응답이 새 선택을 덮어쓰는 일도 막아야 했어요. 응답의 연결 세대와 요청 순번을 현재 요청과 대조했어요. 활성화 직전에는 대상 탭이 현재 창에 남아 있는지도 확인하고, 다른 창이나 앱으로 이동했다면 전환을 취소해요.

Chrome API의 응답이 느린 구간은 호출별로 시간을 나눠봤어요. 탭 정보와 포커스를 확인한 뒤 활성화하는 과정에 포커스 조회가 두 번 있었어요. 첫 조회 뒤에도 비동기 작업이 더 실행되니, 그 결과로는 활성화 직전의 포커스를 보장할 수 없었어요. 마지막 확인을 남기고 중복 조회 한 번을 제거해 API 왕복을 네 번에서 세 번으로 줄였어요.

| Control 해제 → Chrome API 응답 | 변경 전 | 변경 후 |
| ------------------------------ | ------: | ------: |
| 중앙값                         |  24.2ms |  20.8ms |
| p95                            | 140.3ms |  59.7ms |

같은 Mac에서 초당 4~5회 정도 왕복하며 기록한 응답 75개와 129개를 비교했어요. 일부 응답 기록이 빠졌고 입력 속도와 부하도 달라, 수치 차이를 모두 코드 수정의 효과로 볼 수는 없어요. API 응답 기준으로 세운 p95 50ms 목표는 아직 충족하지 못했어요.

## 탭 미리보기에 다른 탭의 화면이 붙지 않도록

전환창에는 탭 제목과 함께 웹페이지의 작은 화면 이미지를 보여줘요. 이 미리보기를 얻으려고 배경 탭을 잠깐 활성화하면, 사용자가 고르는 도중 뒤의 페이지까지 바뀌게 돼요. 그래서 현재 보고 있는 탭만 비동기로 캡처해두고, 전환창에서는 마지막으로 저장한 이미지를 쓰기로 했어요.

여기서도 시작과 완료 시점의 차이를 신경 써야 했어요. A를 캡처하는 도중 B로 이동할 수 있거든요. 완료 시점의 활성 탭만 보고 이미지를 저장하면 A의 화면을 B의 미리보기로 잘못 연결할 위험이 있어요.

캡처를 시작할 때의 상태를 저장하고, 캡처와 이미지 축소가 끝날 때마다 같은지 다시 확인했어요. 탭 ID가 같아도 그 안에서 다른 페이지로 이동했을 수 있으니, 이미지 키에는 연결·창·탭뿐 아니라 페이지 이동을 구분하는 탐색 세대도 넣었어요. 상태가 달라진 결과는 버리고, 저장된 캡처가 없거나 캡처할 수 없는 페이지는 제목과 아이콘만 보여줘요.

## 보조 앱을 더하니 설치와 복구도 챙겨야 했어요

키 입력을 처리할 앱이 생기니 설치와 복구에서도 할 일이 늘었어요. 개발용 서명이 바뀌면 접근성 권한을 다시 등록해야 했고, 앱을 종료했는데 Native Host가 다시 실행하는 버그도 만났어요. 명시적으로 종료했다는 상태를 저장하고, 사용자가 앱을 직접 열면 해제하도록 고쳤어요.

연결이 예기치 않게 끊긴 것과 사용자가 앱을 끝낸 것은 구분해야 했어요. 연결을 복구하려고 만든 자동 실행이 사용자의 종료 의사까지 덮어쓰면 안 되니까요.

현재 제 Mac에서는 빠른 왕복과 후보 선택·취소, 전체화면과 다중 모니터에서의 표시, 탭 이동·삭제와 연결 복구를 확인했어요. 다른 Mac의 최초 설치와 일부 권한·연결 경합은 검증이 남아 있어요. 지원 범위는 macOS와 Chrome이며, 아직 일반 사용자 배포 전 단계예요.
