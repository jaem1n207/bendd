[지난 글](https://bendd.me/craft/bringing-arc-tab-switching-to-chrome)에서는 Arc에서 쓰던 탭 전환을 Chrome으로 가져왔어요. `Ctrl+Tab`을 누르고, 후보를 고르고, 손을 놓는 순간까지 이어지는 경험을 옮기는 작업이었어요.

탭 전환을 채우고 나니, 영상을 볼 때마다 또 하나의 빈자리가 느껴졌어요. Arc의 자동 PiP예요.

영상을 보다가 다른 탭에서 자료를 찾거나 다른 앱으로 이동하면, 영상이 작은 창으로 따라 나왔어요. 원래 화면으로 돌아오면 다시 들어갔고요. PiP 버튼을 찾아 누르거나 창을 닫는 일을 따로 생각하지 않아도 됐어요.

Chrome에도 PiP를 여는 방법은 있었어요. 제가 사용한 환경에서는 실험적 플래그인 `Auto picture in picture on window occluded`와 `Browser initiated automatic picture in picture`를 켜면, 조건을 만족하는 영상이 Chrome에 내장된 PiP로 자동 전환됐어요. [Picture in Picture - Floating player](https://chromewebstore.google.com/detail/picture-in-picture-floati/adnielbhikcbmegcfampbclagcacboff) 같은 확장 프로그램을 이용하는 방법도 있었고, `Alt + P`, macOS에서는 `⌥ + P` 단축키로 PiP를 열 수도 있었어요.

그런데 제게는 내장 PiP의 조작감이 불편했어요. 작은 창을 원하는 자리로 옮기는 과정이 매끄럽지 않았고, 창이 모니터 밖으로 나갔을 때는 직접 다시 옮기지 않아도 화면 안으로 돌아오길 바랐어요. 기존 PiP의 딱딱한 인상도 바꾸고 싶었어요.

그래서 Auto PiP Master를 만들기 시작했어요. 영상을 떠나고 돌아오는 순간에 맞춰 자동으로 열리고 닫히는 것, 그리고 한 번 열린 창을 편하게 옮기고 조작하며 쓸 수 있는 것. 이 두 가지가 Auto PiP의 목표였어요.

만들면서는 ‘다른 앱에서 타이핑하던 흐름은 어떻게 지킬까’라는 질문이 생겼어요. 자동 PiP가 필요한 순간은 사용자가 다른 탭이나 앱으로 주의와 시선을 옮긴 뒤예요. 문서를 읽거나 글을 쓰려는 그곳에 키보드 포커스도 남아 있어야 해요. 작은 창이 열리면서 포커스를 가져가면, 사용자는 방금 선택한 곳을 다시 클릭해야 하니까요. 영상은 곁에서 이어지되 새로 시작한 작업에 집중할 수 있도록 만들고 싶었어요.

나중에는 제 눈에 원본 영상이 전혀 보이지 않는데도 자동 PiP가 나오지 않는 상황을 만났어요. 다른 창이 Chrome을 완전히 덮었지만 브라우저는 가려진 것으로 판단하지 못하고 있었어요. ‘사용자 눈에는 안 보이는데, 브라우저는 왜 보인다고 할까’라는 질문은 여기서 나왔어요. 사람이 보는 화면과 프로그램이 판단하는 가림 상태가 어디서 달라지는지 알아봐야 했어요.

## 영상을 떠나도 시청은 이어지고 싶었어요

원했던 동작을 먼저 적어봤어요.

- 재생 중인 영상을 떠나면 별도의 PiP 클릭 없이 열려요.
- 원본으로 돌아오면 확장 프로그램이 자동으로 연 창을 닫아요.
- 미리 일시정지한 영상은 재생시키지 않아요.
- 사용자가 직접 닫은 PiP를 바로 다시 열지 않아요.
- 직접 연 PiP는 자동화가 빼앗거나 닫지 않아요.
- 원본의 음소거·볼륨·재생 상태를 전환 때문에 바꾸지 않아요.

한 줄로 쓰면 간단했어요. 그런데 이 중 하나만 어긋나도 사용자는 자동화의 다음 행동을 신경 써야 했어요. 닫으면 다시 나타나고, 다른 영상을 재생하면 보던 PiP가 사라지고, 작은 창이 열린 뒤 원래 앱을 다시 클릭해야 한다면 매번 흐름이 끊기니까요.

가장 먼저 만난 경계는 사용자 동작이었어요. 일반적인 영상 PiP 요청에는 일시적인 사용자 활성화가 필요해요. 재생 버튼을 누른 시점의 자격을 한참 뒤 탭을 떠나는 시점까지 보관할 수는 없어요.

Chrome에는 공식 자동 PiP 경로도 있었어요. `MediaSession`에 `enterpictureinpicture` handler를 등록하면, 조건이 맞을 때 Chrome이 호출해주는 방식이에요. 다만 재생 중인 최상위 프레임 미디어, 최근 가청 상태, 오디오 포커스, 사이트 허용이나 이용 이력 같은 조건이 있어요. 음소거 영상과 iframe까지 같은 범위로 다룰 수 있는 계약은 아니었어요. [Chrome 자동 PiP 문서](https://developer.chrome.com/blog/automatic-picture-in-picture-media-playback)

초기 구현에서는 전환할 때만 `chrome.debugger`로 대상 탭에 연결했어요. `Runtime.evaluate({ userGesture: true })`로 PiP 요청을 전달하고, 처리가 끝나면 연결을 해제했어요. 별도의 macOS 앱을 설치하거나 Chromium을 직접 빌드하는 범위까지 넓히고 싶지는 않았어요.

이 선택에는 눈에 보이는 비용이 있었어요. Chrome이 확장 프로그램의 디버깅 연결을 안내하는 알림을 표시할 수 있었어요. 연결을 해제한 뒤에도 Chrome이 안내를 잠시 유지하므로, 빠르게 detach한다고 알림까지 즉시 없앨 수 있는 건 아니었어요. 이 안내는 이후에도 fallback 경로의 제약으로 남았어요. [Chrome debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger)

## 다른 영상을 재생했다고, 보던 PiP가 사라지면 안 됐어요

영상 탭이 두 개 이상일 때는 어떤 영상을 PiP에 남길지부터 정해야 했어요. A와 B는 서로 다른 영상을 재생할 수 있는 탭이고, C는 영상을 보지 않고 문서를 읽는 일반 탭이라고 해볼게요.

먼저 A 탭에서 영상을 보다가, 아직 영상을 재생하지 않은 B 탭으로 이동해요. 화면에서 A 영상이 사라졌으니 A의 PiP가 자동으로 열려야 해요. 여기까지는 영상 하나를 볼 때와 같아요.

이제 B 탭에서도 다른 영상을 재생해요. B 영상은 현재 탭의 플레이어에서 이미 보고 있으니, A의 PiP는 그대로 두고 싶었어요. A는 작은 창에 남겨두고 B는 탭에서 보는 거예요. 그런데 B에서 재생 버튼을 누르는 순간, 잘 나오던 A의 PiP가 사라졌어요.

제가 교체를 기대한 시점은 그다음이었어요. B를 보다가 C의 문서를 읽으러 이동하면 B 영상도 화면에서 사라져요. 이때 A 대신 방금까지 보던 B를 PiP로 보여주면 돼요. **최근에 보던 영상을 떠나는 순간, 그 영상이 PiP를 이어받도록 하고 싶었어요.**

기존 구현은 새 영상 탭을 우선 후보로 기억하는 일과, 다른 탭의 자동 PiP를 닫는 일을 한데 처리하고 있었어요. B의 재생 이벤트가 들어오면 ‘다음에 PiP로 보여줄 후보는 B’라고 기록하면서 A의 PiP까지 닫았어요. B를 계속 보고 있는 동안에는 후보 정보만 바꾸면 되는데, 창의 수명까지 바꿔버린 거예요.

기존 테스트도 B의 재생 뒤 A의 PiP가 닫히는 것을 정상 동작으로 검사하고 있었어요. 테스트가 통과한다는 사실만으로 제가 기대한 시청 흐름까지 맞는 것은 아니었어요.

방문 순서를 기록하는 일과 실제 PiP를 교체하는 일을 분리했어요. B의 재생이 시작돼도 A의 PiP는 유지하고, B를 떠나 C로 이동할 때 B의 PiP를 요청하도록 바꿨어요. 이때도 기존 A부터 닫지 않았어요. 새 요청이 실패하면 A라도 계속 볼 수 있도록 남겨두고, B로 전환할 수 있을 때 교체했어요.

C에서 원본 B 탭으로 돌아오면 B 영상을 탭에서 다시 볼 수 있으니 자동 PiP를 닫아요. 이전 A의 PiP까지 다시 꺼내지는 않아요. 원본으로 돌아온 순간에는 작은 창도 정리돼야, 지금 보고 있는 영상에 맞춰 동작을 예상할 수 있으니까요.

이 우선순위에는 MRU(Most Recently Used), 최근 사용 순서를 적용했어요. 기준은 사용자가 영상 탭을 방문하고 떠난 순서예요. 백그라운드의 A에서 미디어 이벤트가 늦게 도착했다고 해서, 더 최근에 보던 B의 우선순위를 빼앗으면 안 됐어요. 탭의 `lastAccessed`와 실제 Chrome 창 방문 시각을 함께 사용하고, 마지막으로 떠난 영상 탭과 그 방문 시각을 저장했어요.

### 빠르게 왕복하자, 테스트가 놓친 마지막 상태가 나왔어요

그런데 A와 B를 빠르게 여러 번 왕복한 뒤 B 탭에 머물자, A의 PiP가 다시 열리지 않았어요. 마지막으로 떠난 영상 탭이 A이므로 B를 보는 동안에는 A의 PiP가 보여야 했어요. 기존 테스트는 왕복 뒤 C의 문서 탭으로 이동하며 끝났기 때문에, B 탭에 머무르는 경우를 놓쳤어요.

원본 A 탭이 잠깐 보일 때 A의 PiP가 닫히는 것은 정상이었어요. 문제는 다시 B로 이동한 뒤였어요. 화면에 보이는 B가 PiP 우선순위를 미리 가져가고, A를 다시 방문한 시각까지 비교에 섞이면서 방금 떠난 A의 PiP 요청을 막고 있었어요.

탭으로 돌아왔을 때는 그 탭에서 자동으로 열었던 PiP를 먼저 닫도록 했어요. 그 탭을 다음 PiP 후보로 정하는 일은 다시 떠나는 순간까지 미뤘고요. A에서 B로 끝나는 경우와 B에서 A로 끝나는 경우를 각각 검사했어요. 빠르게 왕복하는 동안뿐 아니라, 손을 멈추고 한 탭에 머문 뒤에도 알맞은 영상의 PiP가 남아 있어야 했어요.

### PiP를 옮겼을 뿐인데 다른 영상으로 바뀌었어요

A의 PiP를 유지한 채 B 탭에서 B 영상을 보고 있을 때도 문제가 나왔어요. A의 작은 창을 마우스로 옮겼을 뿐인데 PiP가 사라졌어요.

이벤트 기록을 보니 B 탭은 계속 화면에 보이는 상태였어요. 다만 PiP를 잡는 순간 B가 잠깐 포커스를 잃었어요. 그 변화를 ‘B 영상을 떠났다’고 해석해 교체 요청을 보냈고, B로 포커스가 돌아올 무렵 요청이 끝나면서 새 PiP도 곧바로 닫혔어요.

**포커스가 움직였다는 사실만으로 영상을 떠났다고 판단한 게 문제였어요.**

페이지의 숨김 상태와 일반 Chrome 창 방문을 함께 확인했어요. PiP를 조작하느라 생긴 포커스 변화가 새로운 영상 선택으로 이어지지 않게 했어요. Chrome이 Document PiP도 `type: normal`, `alwaysOnTop: true`인 창으로 보고한다는 점도 발견했어요. 작은 PiP에 포커스를 준 일을 일반 브라우저 창을 새로 방문한 것으로 세면 MRU가 다시 흔들렸어요.

사용자가 직접 연 창, 자동으로 연 창, 현재 탭에서 보고 있는 영상은 각각 유지하거나 닫아야 할 시점이 달랐어요. 이 구분은 뒤의 모든 수정에서 계속 따라다녔어요.

## 같은 조작감을 위해 커스텀 PiP를 만들었어요

자동으로 PiP가 나타나는 것만큼, 열린 창을 편하게 쓰는 것도 중요했어요. 시청을 방해하지 않도록 버튼에 반투명한 배경을 적용하고, 재생·일시정지와 앞뒤 이동, 재생바, 원본 복귀·닫기처럼 PiP에서 필요한 조작만 남겼어요. 창과 버튼에는 전체적으로 둥근 인상을 주고, 볼륨·음소거 조작은 제외해 심플하게 만들었어요.

위치와 크기도 사용자의 선택을 기억하고 싶었어요. 한 번 보기 편한 자리와 크기로 맞췄다면, 다른 탭의 영상으로 PiP를 열어도 같은 자리에 익숙한 크기로 나타나야 했어요. 매번 창을 찾아 옮기고 다시 늘리는 일을 줄이고, 다음에도 어디에 나타날지 예측할 수 있도록요.

기본 영상 PiP의 컨트롤은 브라우저가 그려요. 페이지의 CSS로 버튼을 골라 지울 수 없었어요. 임의의 HTML을 넣는 [Document Picture-in-Picture API](https://developer.chrome.com/docs/web-platform/document-picture-in-picture)를 사용해 별도의 플레이어를 만들었어요.

여기서도 원본을 어디에 둘지 선택해야 했어요. 모든 사이트의 video 요소를 새 문서로 옮기면 사이트가 기대하는 DOM 위치를 깨뜨릴 수 있었고, 다른 출처의 iframe은 또 다른 제약이 있었어요.

일반 영상은 원본 요소와 소리를 원래 탭에 남겼어요. 초기에는 영상 track만 로컬 WebRTC로 전달해 작은 창에서 보여줬어요. 외부 STUN·TURN 서버를 쓰지는 않았지만, 같은 브라우저 안에서도 인코딩·전송·디코딩과 재생 큐의 비용은 생겼어요. 재생·일시정지·탐색 명령은 원본으로 전달했어요.

설정도 조작과 함께 움직여야 했어요. 앞뒤 이동은 기본 5초로 두고, 팝업에서 1~60초의 정수로 바꿀 수 있게 했어요. 이미 열린 PiP의 버튼 숫자와 실제 이동량, 좌우 방향키까지 곧바로 바뀌게 했어요. 설정을 적용하려고 창을 닫았다 다시 여는 동작은 넣지 않았어요.

### 소리가 유지된다는 것과 싱크가 맞는다는 것은 달랐어요

원본의 `muted`와 `volume`이 그대로라는 사실만으로 출력까지 정상이라고 말하고 싶지는 않았어요. 실제 영상으로 PiP와 탭 복귀를 반복하고, 테스트 Chrome 앱의 출력 오디오를 수집해 원본 파형과 비교했어요.

측정 도구에서도 막혔어요. 처음에는 PiP를 쓰기 전의 일반 재생과 440Hz 기준음까지 모두 0으로 수집됐어요. 제품이 소리를 없앴다고 결론 내릴 상황은 아니었어요. 같은 필터와 recorder를 유지한 채 Chrome을 macOS의 정상 앱 실행 경로인 LaunchServices로 시작하자 기준음이 잡혔어요. 그 경로에서 실제 예고편을 다시 측정했어요. 실행 방식과 오디오 수집의 연관은 확인했지만, OS 내부 원인까지 확정한 건 아니에요.

초기 WebRTC 경로의 별도 측정에서는 추가 영상 전달 지연이 중앙값 약 51ms로 추정됐어요. 오디오는 원본에서 계속 나오는데 영상에는 전달 경로가 하나 더 있었어요.

상위 문서와 열린 Shadow DOM에서는 이 경로를 줄일 수 있었어요. `requestVideoFrameCallback`마다 원본의 최신 디코딩 프레임을 PiP의 canvas에 바로 그리도록 바꿨어요. 재인코딩과 수신 디코더, 두 번째 video 재생 큐를 걷어냈어요. 늦은 프레임을 차곡차곡 쌓아 따라잡게 하지 않고, 그릴 때마다 최신 프레임을 사용했어요.

```text
초기: 원본 video → 영상 track → 로컬 WebRTC → 수신 video
개선: 원본 video의 디코딩 프레임 → PiP canvas
오디오: 원래 탭의 원본 video에서 계속 출력
```

두 방식에서 같은 이미지 171개를 짝지어 소프트웨어 관측 시각을 비교했을 때, 직접 표시가 중앙값 18.30ms 빨랐어요. 다만 앞의 51ms와 측정 방식이 달라 두 수치를 빼서 남은 지연을 계산할 수는 없어요. 물리 스피커와 패널의 절대 립싱크를 측정한 것도 아니고요.

iframe에는 기존 로컬 WebRTC 경로를 유지해 추가 영상 전달 지연이 남았어요. canvas의 `desynchronized: true`도 지연을 줄이기 위한 힌트일 뿐, 0ms를 보장하는 옵션은 아니에요.

### 테스트 영상과 측정 도구도 의심해야 했어요

재생바가 안 움직이는 실패 중에는 제품 밖의 원인도 있었어요. 합성 MP4 서버가 HTTP byte-range 응답을 지원하지 않아, 원본부터 탐색 가능한 구간이 `[0, 0]`으로 나왔어요. 서버를 고친 뒤 실제 seekable 구간을 요구하며 다시 검사했어요. 탐색할 수 없는 원본의 버튼을 억지로 활성화하지는 않았어요.

오디오 녹음에서는 영상을 멈춘 대조 구간에도 신호가 남은 실행이 있었어요. 그런 녹음의 ‘무음 없음’을 정상 재생의 근거로 쓰지 않았어요. 앞뒤 대조가 0인지 확인하고 새로 측정했어요.

분석 해상도에 따라 파형 일치가 불확실해진 구간도 있었어요. 판정 기준을 낮추는 대신, 같은 녹음을 더 높은 해상도로 분석하고 짧은 끊김을 계속 검출하는지 별도로 확인했어요. 작은 플레이어를 만드는 일에 측정 도구의 신뢰성까지 따라올 줄은, 구현만 볼 때는 잘 드러나지 않았어요.

## 창을 열고 난 뒤에도 손은 원래 작업을 이어가야 했어요

영상 전달 지연을 줄여도, 창이 열릴 때 읽던 문서의 키보드 포커스가 사라지면 불편했어요. 문서는 눈앞에 있는데 다음 `Ctrl+Tab`이 의도대로 작동하지 않았어요.

일반 `documentPictureInPicture.requestWindow()` 요청은 새 창을 활성화할 수 있었어요. 당시 공개 옵션에는 `focus: false`가 없었어요.

Chrome 안의 탭 전환에서는 PiP 요청 직전 읽던 일반 창을 기억했어요. 생성 후 새 PiP가 여전히 포커스를 갖고, 그 사이 사용자가 PiP를 직접 조작하지 않았을 때 한 번만 원래 창으로 돌렸어요. 활성 탭을 지정하지 않아 읽던 문서와 입력 필드를 유지했어요.

복원도 자동화라서 조심해야 했어요. PiP가 준비되는 동안 사용자가 다른 Chrome 창을 선택했다면 최신 선택을 따라야 했어요. renderer에 복원 가능 여부를 물은 뒤 최신 창 상태를 다시 확인했어요. PiP를 직접 클릭한 경우나 다른 앱으로 떠난 경우에는 과거 창으로 끌고 오지 않도록 했어요.

생성 순간 들어온 키는 PiP를 선택했다는 의도로 세지 않았어요. 반대로 사용자가 직접 PiP를 클릭한 뒤에는 그 조작을 존중했어요. 포커스를 반복해서 되돌리는 루프는 만들지 않았어요.

검증할 때는 특정 페이지에 CDP 키를 보내는 것만으로 충분하지 않았어요. 그 방법은 실제 OS 키보드 포커스가 잘못돼도 원하는 페이지에 입력을 전달할 수 있었어요. 테스트 Chrome의 실제 key window에 `Ctrl+Tab`을 보내고, 원래 읽던 탭의 다음 동작까지 확인했어요.

이 수정은 Chrome 안에서 읽던 창을 복구한 것이에요. 다른 앱의 포커스나 macOS의 앱 전환 순서까지 복구한 것은 아니었어요. 그 경계가 곧 다음 문제로 나타났어요.

## 작게 움직여도 같은 규칙으로 반응하도록 다듬었어요

PiP는 작은 창이라 사소한 조작 차이도 크게 느껴졌어요. 버튼 하나를 누른 뒤 방향키가 안 먹거나, 마우스를 놓았는데 창이 한동안 움직이면 조작을 다시 확인하게 됐어요.

Arc에서 테스트 영상을 재생하며 컨트롤의 배치와 동작을 살펴보고, 설치 리소스의 아이콘도 참고했어요.

재생과 일시정지 아이콘은 같은 SVG path를 변형했어요. 전환 중 다시 누르면 현재 모양에서 반대 상태로 이어지게 했어요. reduced motion 설정에서는 바로 최종 모양을 보여줬어요.

재생 버튼을 클릭한 뒤에도 Space와 좌우 방향키가 동작하도록 고쳤어요. Space가 버튼의 기본 클릭과 중복 실행되지 않게 하고, 복귀·닫기 버튼과 입력 필드의 기본 키보드 동작은 유지했어요. 빠르게 Space를 연속 입력할 때 이전 재생 상태로 다음 명령을 계산하던 경합도 원본의 동기 `paused` 상태를 바로 전달해 수정했어요.

### 마우스를 놓았는데, 창은 아직 움직이고 있었어요

드래그 중 native 창 이동 요청을 모두 Promise 큐에 넣으면 지나간 좌표까지 순서대로 실행돼요. 마우스를 놓은 뒤에도 처리가 남을 수 있었어요.

진행 중인 호출 하나와 최신 좌표 하나만 유지하도록 바꿨어요. 드래그가 끝나면 대기 타이머와 여러 단계의 이동을 거치지 않고 최종 가시 위치로 맞췄어요. 모니터를 넘어갈 때 필요한 Chrome의 화면 선택과 마지막 경계 보정은 따로 처리했어요.

화면 밖 좌표 요청을 Chrome이 거절하는 경우도 있었어요. 실패했다고 종료 좌표를 버리지 않고 마지막으로 유효했던 화면 안에서 복구했어요. 이전 크기 변경 요청이 늦게 끝나 새로 드래그한 위치를 덮는 문제도, 최신 사용자 위치를 우선하도록 고쳤어요.

두 모니터 경계에 걸쳐 놓는 조건도 확인했어요. 추가 화면에 40% 걸쳤을 때와 60% 넘어갔을 때 돌아가는 화면이 달랐어요. 확장 프로그램이 임의로 화면 목록 권한을 더 요청하기보다 Chrome이 선택한 현재 화면을 사용했어요.

### 세로로 50px 움직였는데 12px만 커졌어요

초기에는 직접 만든 모서리 핸들로 비율을 유지하며 크기를 조절했어요. 그런데 포인터 이동을 비율 선에 투영하자, 16:9 영상에서 세로로 50px 움직여도 높이가 약 12px만 늘었어요.

수학적으로 비율을 지켰지만 손이 기대한 변화와는 달랐어요. 세로 이동을 너비 변화로 환산하고 주로 움직인 축을 따르도록 바꿨어요. 실제 세로 50px 입력 뒤 내용 높이가 50px 증가하는지 확인했어요.

이 커스텀 핸들은 이후 제거했어요. Chrome의 기본 테두리 조절과 휠 확대·축소를 함께 다듬으면서, 기본 테두리를 사용하고 조절이 멈춘 뒤 원본 비율을 보정하는 구조를 택했어요.

### 휠과 테두리의 최대 크기가 달랐어요

휠로 키울 때와 테두리로 늘릴 때 도달하는 크기가 달랐어요. 제 계산만 다른 게 아니었어요. 확인한 Chromium 구현은 프로그램의 크기 요청을 화면 면적의 25%로, 사용자 직접 조절을 각 축의 80%로 제한하고 있었어요.

휠의 상수만 키워도 프로그램 요청이 그 크기에 도달하지 못했어요. 실제로 더 큰 공통 상한을 시도했지만 두 조작의 결과가 달라 최종 구현에 사용하지 않았어요.

프로그램으로도 도달 가능한 25% 면적 범위를 공통 상한으로 정했어요. Chrome의 표시줄·테두리까지 포함한 외곽 면적과 영상 내용의 비율을 함께 계산했어요. 사용자가 더 크게 늘려도 조절이 끝나면 공통 범위 안으로 들어오게 했어요. [당시 Chromium 크기 제한 구현](https://chromium.googlesource.com/chromium/src/+/4c325193fa2320d5732c3110c6eba0487467a10d/chrome/browser/picture_in_picture/picture_in_picture_window_manager.cc)

기본 테두리의 정확한 마우스 해제 이벤트는 공개 창 API로 받지 못했어요. 마지막 크기 변경이 120ms 동안 멈추면 보정했어요. 위치를 옮기고 놓았을 때의 즉시 보정과, 테두리 크기 조절의 정지 감지는 다른 동작이에요.

Chrome 안내 표시줄이 나타날 때 바깥 창 크기는 그대로인데 내용 영역만 줄어드는 실패도 있었어요. `windows.onBoundsChanged`만 기다리면 놓쳤어요. viewport와 native 프레임 두께의 변화를 함께 감지해 영상 비율을 다시 맞췄어요. 최대 크기에서 표시줄이 사라지면 새 내용 영역에 맞춰 상한도 다시 계산했어요.

### 마지막 배치를 기억하되, 복원이 새 기본값이 되지는 않게 했어요

A 영상에서 위치와 크기를 맞췄는데 B 영상을 열 때 다시 기본 420px로 시작하면 조절을 반복해야 했어요. 사이트별 초기값 대신 마지막으로 사용자가 조절한 배치를 공통으로 기억했어요.

저장한 것은 창 좌표와 작업 영역, 영상 내용 너비였어요. 다른 비율의 영상은 같은 내용 너비를 기준으로 높이를 다시 계산했어요. 브라우저 표시줄 높이가 달라져도 영상 크기를 유지하려고 했어요.

모니터를 급히 옮긴 직후 닫는 경우에는 새 좌표와 이전 화면 정보가 섞일 수 있었어요. 화면 정보가 확정되지 않았다면 절대 좌표를 저장하고, 다음에 실제로 연결된 작업 영역 안으로 보정했어요. 자동 복원 중의 좌표를 다시 사용자의 새 선택으로 저장하지도 않았어요.

Minimize 버튼은 제거했어요. 처음의 ‘접기’와 실제 OS 최소화는 달랐고, Chrome은 PiP 창의 최소화 요청도 거절했어요. 사이트 출처 표시줄 역시 Chrome 소유 UI라 남겼어요. 작은 창 내부의 디자인과 브라우저가 책임지는 창의 경계를 구분했어요. [Document PiP의 출처 표시 요구](https://wicg.github.io/document-picture-in-picture/#origin-visibility)

## Netflix에서도 같은 작은 창을 쓰고 싶었어요

일반 영상에서 만든 커스텀 플레이어를 Netflix와 쿠팡플레이에서도 쓰고 싶었어요. 하지만 보호된 미디어에서는 프레임을 캡처하는 방식이 막혔어요. 이때 기본 영상 PiP로 표시할 수 있더라도, 사이트에 따라 컨트롤과 크기 조절 방식이 달라졌어요.

보호된 프레임을 복사하는 방향은 사용하지 않았어요. 두 서비스의 최상위 영상에 한해서, 재생 중인 **같은 video 요소를 Document PiP로 옮겼다가 돌려놓는 방식**을 선택했어요. 정확한 네 hostname으로 범위를 제한했어요.

같은 요소와 MediaKeys를 유지하므로 새로운 영상을 만들거나 재생을 복제하지 않아요. 원래 parent와 sibling, 스타일과 controls 속성을 보관하고, 복귀·닫기·교체·오류 때 원래 위치로 복원했어요. 원본 음소거와 볼륨, 탭 음소거는 바꾸지 않았어요.

일반 사이트에서는 원본을 남기는 쪽을 택했고, 두 서비스에서는 같은 UI를 제공하기 위해 요소 이동의 비용을 받아들였어요. 하나의 구현을 모든 사이트에 적용하는 대신, 예외의 범위와 복원 책임을 함께 정했어요.

복원에도 함정이 있었어요. 사이트가 원래 플레이어 컨테이너를 교체한 뒤 옛 요소를 무조건 붙여놓으면, 새 플레이어 옆에 이전 영상이 살아날 수 있었어요. 원본 위치가 사라졌는지 감시하고, 중첩 Shadow DOM의 상위 위치 제거도 따라가도록 했어요.

요소를 다른 문서로 옮긴 뒤 탐색 간격이 계속 5초에 남는 버그도 나왔어요. 다른 Window realm에서 만들어진 `CustomEvent`를 기존 문서의 `instanceof CustomEvent`로 검사하고 있었어요. 같은 종류의 이벤트여도 생성자 객체가 달랐어요. 필요한 숫자 detail과 현재 세션을 검사하는 방식으로 바꿨어요. 기본 자동 경로의 휠 명령에서도 같은 종류의 경계를 확인했어요.

합성 영상에 실제 ClearKey MediaKeys를 연결한 검사는 같은 요소·키·재생 상태의 보존을 확인하는 데 사용했어요. 실제 서비스의 암호화된 본편이나 라이선스 교환을 재현한 검사는 아니었어요. 이후 직접 사용하면서 Netflix와 쿠팡플레이의 커스텀 UI·영상·원본 복귀가 정상임을 확인했어요.

### 버튼은 되는데, Netflix 재생바는 멈췄어요

Netflix에서 앞뒤 이동 버튼과 재생·일시정지는 동작했어요. 그런데 재생바는 가까운 곳을 눌러도, 먼 곳을 눌러도, 드래그해도 영상이 멈추고 목표 위치로 가지 않았어요.

합성 MP4에서는 같은 range 입력이 정상 동작했어요. 일반 재생바 이벤트만 고칠 문제라고 단정할 수 없었어요. 기존 버튼과 재생바 모두 `video.currentTime`을 직접 바꾸고 있었지만, 서비스가 관리하는 재생 세션과 동기화되는 경로가 따로 필요할 수 있었어요.

[재생 세션의 `seek()`를 사용하는 공개 구현](https://github.com/Cifer-Y/netflix-loop/blob/main/page.js)에서 단서를 얻어, Netflix 플레이어의 재생 세션을 통해 탐색하는 어댑터를 분리했어요. 다만 이 내부 API는 Netflix가 안정성을 보장하는 공개 API는 아니에요.

실제 사이트를 통째로 흉내 내는 대신, 서비스가 관리하는 시계와 video의 시계가 다른 합성 모델을 만들었어요. 서비스 시계가 먼저 갱신되고 video가 늦게 따라오는 조건에서는 연속 탐색의 마지막 위치가 어긋나는 실패를 재현했어요.

초와 밀리초 단위를 변환하고, 시계의 원점 차이를 PiP 세션에 묶어 유지했어요. 재생바를 잡고 움직이는 동안에는 목표 위치만 미리 보여주고, 놓을 때 한 번 확정했어요. 취소된 포인터 입력은 실행하지 않았어요. 요청은 같은 세션 안에서 순서를 지키되, 끝나지 않는 요청 때문에 새 세션까지 막히지 않도록 분리했어요.

현재 소유한 최상위 영상과 재생 세션이 맞는지 다시 확인하고, 세션이 모호하거나 내부 API가 없으면 오류로 남겼어요. 실패한 뒤 같은 `currentTime` 변경을 다시 시도해 원래 문제로 돌아가지는 않았어요.

합성 모델에서는 클릭·드래그·키보드 탐색을 확인했어요. 수정한 어댑터가 실제 Netflix 재생바에서도 동작하는지는 추가 확인이 필요해요. 서비스 내부 API에 의존하므로 Netflix 플레이어가 바뀌면 어댑터도 함께 대응해야 해요.

### 한 편이 끝났다고, 시청까지 끝난 건 아니었어요

다음에는 YouTube와 Netflix의 연속 재생에서 창이 사라졌어요. A가 끝나면 커스텀 PiP가 닫혔고, 다음 영상이나 다음 화가 시작돼도 돌아오지 않았어요. 확장 프로그램을 끄고 Chrome의 기본 PiP와 비교하면 기존 창에서 다음 영상이 이어졌어요.

확장 프로그램은 `ended`, `emptied`, 캡처 track의 종료를 각각 정리 신호로 처리하고 있었어요. 일부 자동 정리는 사용자 닫기처럼 해석돼 다음 PiP까지 억제했어요. [미디어 요소 캡처의 track 수명](https://www.w3.org/TR/mediacapture-fromelement/#html-media-element-media-capture-extensions)도 영상 하나의 재생 수명과 연결돼 있어, 종료된 track을 계속 쓰는 방식으로는 충분하지 않았어요.

창의 수명과 영상 하나의 수명을 나눴어요. 종료·소스 변경 뒤에는 최대 30초 동안 다음 재생을 기다렸어요. 종료 이벤트 없이 요소나 원래 위치가 사라진 경우에는 최대 5초의 교체 유예를 뒀어요. 반복 이벤트가 와도 기한을 계속 늘리지는 않았어요.

같은 video의 소스가 바뀌면 다시 검증하고, 새로운 video로 바뀌면 같은 frame과 이탈 주기의 후보인지 확인해 token·컨트롤·영상 연결을 넘겼어요. iframe의 RTC 경로는 기존 sender의 video track을 교체했어요. OTT 요소 이동 경로는 이전 요소를 복원하고 다음 요소의 원래 위치를 따로 보관해 같은 창으로 옮겼어요.

창과 세션은 유지했어요. 사용자 닫기와 원본 복귀는 대기까지 취소했어요. 다음 영상이 끝내 없으면 그때 정리했어요. 전체 페이지가 바뀌어 opener 문서가 종료되는 경우까지 같은 창을 유지한다는 의미는 아니에요.

실제로 YouTube의 다음 영상과 Netflix의 다음 화가 **기존 커스텀 PiP에서 이어지는 것**을 확인했어요. 새 창이 다시 뜨는 것과 같은 창에서 시청이 이어지는 것의 차이는 작지 않았어요.

## 다른 앱으로 갔다가 돌아오려는데, Chrome이 먼저 돌아왔어요

Chrome 안에서 읽던 탭의 포커스를 복구하는 데는 진전이 있었어요. 그런데 다른 앱으로 이동할 때는 문제가 더 커졌어요.

다른 앱을 선택하고 작업을 시작했는데, 조금 뒤 커스텀 PiP가 열리면서 Chrome이 다시 활성화됐어요. macOS의 앱 전환 순서도 달라져, 원래 생각한 창으로 돌아가려면 `Cmd+Tab`을 한 번 더 눌러야 하는 상황이 생겼어요.

Chrome의 탭 MRU를 바로잡는 것과 macOS의 앱 MRU를 지키는 것은 다른 일이었어요. 확장 프로그램의 창 API에서 Chrome 창을 다시 선택했다고 외부 앱의 입력까지 복구되는 것도 아니었어요.

처음에는 창을 만들고 곧바로 포커스를 돌리면 될 것 같았어요. 하지만 `window.blur()`나 `chrome.windows.update({ focused: false })`로 원래 외부 앱을 되살리는 경로는 확인하지 못했어요. API 응답이 성공해도 실제 macOS에서 어느 앱이 활성인지 따로 확인해야 했어요.

Chrome의 자동 PiP callback으로 커스텀 창을 열 때는 비활성 생성이 가능했어요. 일반 fallback 요청으로 같은 Document PiP를 열면 Chrome이 활성 표시를 선택했어요. 같은 UI를 그려도 **어떤 생성 경로를 탔는지**가 포커스 동작을 바꾸고 있었어요.

### 대안을 하나씩 검토할수록, 포기할 경험이 보였어요

다른 앱에서의 fallback만 기본 영상 PiP로 바꾸는 방법도 검토했어요. 격리 실험에서 기본 영상 PiP는 외부 앱의 활성 상태를 유지했어요. 대신 사용자가 이동한 경로에 따라 컨트롤과 탐색·크기 조절 방식이 달라졌어요. 이번 작업에서는 공통 커스텀 UI를 유지하기로 했어요.

안전한 자동 callback이 없는 상황에서는 자동화를 생략하는 방안도 있었어요. 하지만 가장 필요했던 ‘영상을 보다가 바로 다른 앱으로 이동하는 순간’까지 빠질 수 있었어요. 핵심 상황을 계속 지원하는 방향을 찾고 싶었어요.

Chrome 내부의 탭을 바꾸면 자동 callback이 온다는 점을 이용하는 실험도 했어요. 외부 앱이 활성인 동안 같은 Chrome 창의 다른 탭을 선택하자, 조건이 맞는 합성 영상에서는 커스텀 PiP를 비활성으로 열 수 있었어요. 두 번의 시험에서 외부 앱 포커스도 유지했어요.

그러나 그 대가로 사용자가 다른 앱에 있는 동안 Chrome의 선택 탭을 바꿔야 했어요. 두 모니터에서는 그 변화가 그대로 보일 수 있었고, 돌아올 탭과 `Ctrl+Tab` 순서, 사용자가 직접 한 선택의 복구까지 새로 책임져야 했어요. 일부 성공을 확인한 실험으로 남기고 제품에는 넣지 않았어요.

PiP를 미리 만들어 최소화해뒀다 꺼내는 경로도 막혔어요. Chrome은 `Operation not allowed for picture-in-picture windows`로 최소화를 거절했어요. 구현되지 않은 `focused: false`·`background: true`·`showInactive: true` 필드를 `requestWindow()`에 넣어도 비활성 생성 경로가 생기지 않았어요.

보조 macOS 앱을 쓰면 다룰 수 있는 영역은 넓어져요. 지난 탭 전환 프로젝트에서는 그 비용을 감수했어요. 이번에는 기존 Chrome에 확장 프로그램 하나를 추가하는 범위를 유지하고 싶었어요. 별도 Chromium 빌드나 브라우저 전역 설정을 자동 변경하는 방법도 제품에 넣지 않았어요.

### 빨리 열면 해결될까요

PiP가 한 박자 늦게 나타나는 것도 불편했어요. 다른 앱에 손이 간 뒤에 포커스를 가져가면 방해가 더 또렷해졌어요.

코드에는 native callback을 기다리는 최대 800ms, background의 160ms 예약, content의 80ms 갱신 대기가 있었어요. 이 대기는 서로 겹치고 재예약될 수 있으므로 모두 더한 값이 실제 생성 지연은 아니었어요.

단순히 800ms를 없애는 것으로 포커스 문제를 해결할 수는 없었어요. Chrome이 제공하는 비활성 자동 생성의 기회를 먼저 없애거나, 잠깐 떠났다가 돌아오는 순간에 불필요한 창을 더 빨리 띄울 수도 있었어요.

여기서 지연을 두 갈래로 나눴어요. 원본 프레임을 PiP에 전달하는 지연은 앞에서 직접 표시로 줄였어요. 이번 문제는 **창을 열어도 되는지 판단하고 어느 경로로 생성할지 기다리는 시간**이었어요. 포커스에 대한 잘못된 판단을 빠르게 실행해도 판단 자체는 그대로 남았어요.

### 일시정지한 채 돌아오면, 창이 남았어요

복귀 처리에도 별도의 버그가 있었어요. PiP에서 일시정지하고 다른 앱에 갔다가 Chrome으로 돌아오면 창이 닫히지 않았어요. 즉시 복귀하는 검사에서는 통과해서, 상태의 수명을 더 길게 봐야 했어요.

PiP를 일시정지한 상태에서 service worker를 종료·재시작하자 재현됐어요. 앱을 떠났다는 경계가 worker의 메모리에만 있었어요. 새 worker는 PiP의 focus 이벤트를 받아도 원래 앱으로 복귀한 상황인지 알지 못했어요.

소유 창의 세션에 앱 이탈과 최근 pointer 조작 시각을 함께 저장하고 복원했어요. 첫 focus 메시지가 초기화보다 먼저 처리되지 않도록 순서도 고쳤어요. 복귀한다고 영상을 강제로 재생하지 않았어요. 닫힌 뒤에도 사용자가 선택한 일시정지를 유지했어요.

검사도 한 번 더 고쳤어요. 처음의 통과 실행은 pause 알림으로 worker를 미리 깨운 상태였어요. 그 도움 없이 PiP focus가 첫 이벤트로 worker를 깨우는 조건을 넣고 다시 확인했어요. 실제 사용에서도 `Cmd+Tab` 복귀 뒤 PiP가 닫히고 정지 상태가 남는 것을 확인했어요.

이 버그를 고친 것만으로 앱 이탈 때의 포커스 문제까지 해결한 건 아니었어요. 떠날 때 잘못 활성화되는 문제와, 돌아왔을 때 상태를 잊는 문제를 나눠 추적했어요.

## 점선으로 표시된 탭이 떠올랐어요

여러 방법을 검토하고 나니, 창을 띄운 뒤 포커스를 되돌리는 시도만으로는 채워지지 않는 부분이 남았어요. 판단에 쓸 수 있는 신호를 다른 곳에서 찾아봐야 했어요.

곰곰이 생각을 되뇌다가, 문득 Chrome에서 오래 사용하지 않은 탭의 아이콘이 점선으로 표시되던 모습이 떠올랐어요. 마우스를 올리면 ‘메모리 절약 중’이라는 안내가 나오던 탭이요.

그 자리에서 머리를 탁 치며 궁금해졌어요.

‘이 탭이 지금 일하지 않아도 된다는 건 어떻게 아는 거지?’

‘Chromium 안에는 사용자에게 보이는 상태를 판단하고, 보이지 않는 창의 일을 줄이는 코드도 있지 않을까?’

그렇다면 제가 확장 프로그램 안에서 모든 판단을 새로 만들 필요가 있을까요. 브라우저가 이미 내린 판단을 받아 커스텀 PiP를 연결할 수는 없을까요.

이때의 생각은 출발점이었어요. Memory Saver와 창 가림 감지가 같은 기능이라는 결론은 아니었어요. 실제로 Memory Saver는 비활성 탭의 메모리를 회수하는 정책이고, 재생 중인 오디오·영상 같은 활동은 비활성화를 막을 수 있어요. [Chrome Memory Saver 안내](https://support.google.com/chrome/answer/12929150?hl=en)

그래도 이 질문이 조사할 방향을 바꿔줬어요. 확장 프로그램이 관찰한 focus와 DOM 이벤트 바깥에, 브라우저 자체가 관리하는 가시성 상태가 있었어요.

### `WebContentsObserver`에서 내부 상태를 따라갔어요

Chromium에는 페이지를 담는 `WebContents`의 상태를 관찰하는 C++ 인터페이스인 `WebContentsObserver`가 있어요. macOS의 자동 PiP 가림 helper가 그 observer를 사용하고 있었어요.

상태는 단순한 참·거짓이 아니었어요.

| 내부 상태  | 이 조사에서 구분해야 했던 상황  |
| ---------- | ------------------------------- |
| `VISIBLE`  | 창의 콘텐츠가 보이는 상태       |
| `OCCLUDED` | 다른 창에 가려진 상태           |
| `HIDDEN`   | 탭 선택 해제 등으로 숨겨진 상태 |

가림 helper는 이 변화를 자동 PiP 쪽으로 전달했어요. 활성 탭이 `OCCLUDED`가 되면 진입을 시도하고, `VISIBLE`이 되면 자동 PiP를 종료하는 경로가 있었어요. `HIDDEN`은 그 가림 observer 안에서 새로 열고 닫는 동작을 하지 않고, 탭 전환 경로와 구분됐어요. [Chrome 156의 가림 helper](https://chromium.googlesource.com/chromium/src/+/156.0.8078.74/chrome/browser/picture_in_picture/auto_picture_in_picture_window_occlusion_helper_web_contents.cc), [자동 PiP 정책](https://chromium.googlesource.com/chromium/src/+/156.0.8078.74/chrome/browser/picture_in_picture/auto_picture_in_picture_tab_helper.cc)

`document.hidden`은 이 내부 세 상태를 그대로 노출하는 API가 아니었어요. PiP나 캡처 같은 조건도 DOM 가시성 계산에 영향을 줬어요. `document.hidden === false` 하나로 Chromium 내부에도 가림 신호가 없다고 결론 내릴 수는 없었어요.

게다가 Chrome 내부의 자동 PiP 상태에서 Document PiP를 열면, PiP manager가 비활성 창 표시를 선택했어요. 같은 커스텀 UI를 유지하면서 다른 앱의 포커스를 건드리지 않을 실마리가 여기에 있었어요. 창을 띄운 뒤 되돌리는 우회보다 앞선, 창을 생성하는 단계의 선택이었어요. [버전 고정 PiP manager](https://chromium.googlesource.com/chromium/src/+/156.0.8078.74/chrome/browser/picture_in_picture/picture_in_picture_window_manager.cc)

그때는 그동안 따로 보이던 문제가 한 경로에서 만나는 느낌이었어요. 가림을 제대로 판단하는 일, 다른 모니터의 원본을 그대로 두는 일, 커스텀 UI를 유지하는 일, 외부 앱의 포커스를 지키는 일이요. 개발 일지에서 ‘이 모든 문제를 풀 수 있지 않을까’ 하고 기대했던 지점이었어요.

## Chrome의 판단을 기다리는 것도 구현이었어요

가능성을 찾았다고 기존 확장 프로그램에 플래그 하나를 더해 끝나지는 않았어요.

당시 조사한 두 기능은 역할이 달랐어요. `AutoPictureInPictureOnWindowOccluded`는 창 가림을 자동 PiP의 진입 신호로 연결했어요. `BrowserInitiatedAutomaticPictureInPicture`는 등록된 handler가 없을 때도 Chrome이 기본 영상 PiP를 열 수 있게 하는 별도의 기능이었어요.

소스에서는 등록된 `enterpictureinpicture` handler를 먼저 사용했어요. 그래서 커스텀 UI를 쓰는 데 필요한 핵심은 가림 경로와 기존 handler의 연결이었어요. 두 번째 기능을 켠다고 커스텀 UI가 생기는 구조는 아니었어요. handler가 없는 순간에는 오히려 기본 UI가 열릴 수 있었어요. [Chrome 156의 handler 라우팅](https://chromium.googlesource.com/chromium/src/+/156.0.8078.74/content/browser/media/session/media_session_impl.cc)

창 가림을 자동 PiP에 연결하려면 해당 기능이 활성화돼 있어야 해요. 당시에는 사용자가 직접 `chrome://flags/#auto-picture-in-picture-on-window-occluded`를 켜고 재시작해야 하는 환경이 있었고, 사이트 자동 PiP 허용과 미디어 자격도 필요했어요. 확장 프로그램은 이 전역 설정을 바꾸지 않고 Chrome이 전달하는 callback을 사용해요.

### callback이 없다는 게 실패를 뜻하지는 않았어요

기존 확장 프로그램은 Chrome이 callback을 주지 않으면 일정 시간을 기다린 뒤 debugger fallback을 실행할 수 있었어요. 그런데 다른 모니터에서 원본이 계속 보이는 상황에서는 **callback이 오지 않는 게 올바른 결과**였어요.

포커스를 잃었다는 이유로 기다렸다가 강제로 열면, Chrome의 가림 판단을 연결하고도 확장 프로그램이 그 결정을 덮어쓰게 됐어요.

실제 가림에서도 순서가 문제였어요. 한 수정 전 실행에서는 PiP가 약 973ms에 처음 관측되고 `document.hidden`은 약 1030ms에 관측됐어요. 표본 간격이 있는 telemetry라 내부 callback 시각이나 물리 표시 시간을 뜻하지는 않아요. 그래도 기존 대기 기반 fallback이 가림 경로보다 먼저 들어올 수 있다는 점은 드러났어요.

앱·창 이탈의 자동 생성은 Chrome의 callback에 맡기도록 바꿨어요. callback에서는 이미 만들었던 같은 커스텀 renderer를 사용했어요. debugger fallback은 실제 원본 탭이 비활성이고 일반 Chrome 창에 포커스가 있는 경우에 남겼어요.

핵심 조건은 이렇게 정리됐어요.

```ts
export function debuggerFallbackAllowed(
  sourceTabActive: boolean,
  chromeWindowFocused: boolean
): boolean {
  return !sourceTabActive && chromeWindowFocused;
}
```

이 함수는 가림을 계산하지 않아요. 확장 프로그램이 확실히 판단할 수 있는 Chrome 내부 탭 전환의 보완 범위를 제한해요. 음소거 영상이나 iframe의 기존 보완은 그 범위에 남기고, 외부 앱에 있는 동안 callback 부재를 강제 생성의 허가로 사용하지 않도록 했어요.

### 마지막 확인 뒤에도 사용자는 움직일 수 있었어요

비동기 준비가 끝난 뒤에도 앱이 바뀔 수 있었어요. 영상 캡처 준비를 시작할 때 Chrome이 활성이라고 확인했어도, `requestWindow()`를 호출하는 순간까지 같은 상태인 건 아니었어요.

준비가 끝나는 지점에서 의도적으로 대기시키고 다른 앱으로 이동하는 회귀를 만들었어요. 더 늦게, 원본 검증 응답 직후 이동하는 조건도 넣었어요. 초반 수정은 창을 취소하고도 Chrome이 이미 활성화돼 실패했어요.

실제 요청 바로 앞에서 최신 일반 창 포커스를 다시 확인했어요. 포커스 복원도 renderer의 응답 뒤 최신 창 상태를 읽도록 순서를 고쳤어요. 두 경로의 전역 예약과 세션·주기 토큰으로 중복 생성과 늦은 응답을 정리했어요.

Chrome API 조회와 OS 앱 전환을 하나의 원자적 동작으로 묶는 보장은 없어요. 모든 미세한 타이밍이 완벽하다고 주장할 수는 없었어요. 대신 실제로 발견한 경합을 고정된 실패 조건으로 만들고, 그 경계에서 늦은 생성과 오래된 포커스 복원이 없는지 확인했어요.

검증한 90% 크기의 Chrome을 불투명 외부 창으로 완전히 가리는 조건에서는, 같은 커스텀 UI가 native callback 경로로 열리고 외부 앱의 활성 상태가 유지됐어요. 다른 모니터에서 원본이 보이는 대조에서는 새 PiP가 없었어요. 가림 해제와 반복 가림도 확인했어요.

실제로 사용해보니 `Cmd+Tab`으로 돌아올 때 추가 입력 없이 원래 작업으로 복귀할 수 있었어요.

### 두 모니터에서 동시에 재생하자 기본 PiP가 나왔어요

A 모니터와 B 모니터의 Chrome 창에서 각각 영상을 재생한 뒤, B만 가렸어요. 기대한 건 B의 커스텀 PiP였어요. 그런데 기본 PiP가 나왔어요. A를 정지하면 다시 커스텀이 나왔고요.

원인은 앞서 넣었던 경쟁 방지 규칙이었어요. 브라우저 전체에 가청 탭이 둘 이상이면 모든 커스텀 handler를 해제했어요. 같은 창 안에서 수동 PiP와 MRU가 충돌하는 조건을 다루려고 넣었던 제한이, 서로 다른 모니터의 독립된 창까지 묶고 있었어요.

제한 범위를 **같은 Chrome 창 안의 가청 탭 경쟁**으로 좁혔어요. 서로 다른 창은 각각 handler를 유지하고, 탭을 다른 창으로 옮길 때도 다시 계산했어요.

같은 두 모니터 조건에서 B를 가리고 드러내는 과정을 반복했어요. B는 커스텀 PiP로 이어지고 A의 재생과 음량은 유지됐어요. UI 일관성을 지키려면 renderer만 같아서는 부족했어요. 그 renderer까지 도달하는 자격과 handler 등록 정책도 같은 사용자 상황을 구분해야 했어요.

## 눈에는 안 보이는데, API는 보인다고 했어요

다음 실험에서는 Chrome을 줄이지 않았어요. 같은 Space에서 화면 작업 영역을 100% 채우고, 같은 크기의 일반 외부 창으로 덮었어요. 여기서 100%는 녹색 버튼으로 별도 Space에 들어가는 macOS 전체화면과는 달라요.

Chrome을 90% 크기로 두고 큰 창으로 덮었을 때는 자동 PiP가 나왔어요. 그런데 둘의 외곽을 같게 맞추자 나오지 않았어요. 확장 프로그램을 끈 Chrome 기본 PiP도 같은 조건에서 나오지 않았어요.

확장 프로그램이 수집한 상태를 보니 재생 중인 영상과 handler는 계속 준비돼 있었어요. callback을 직접 추적해도 일반 창의 동일 크기 가림에서는 호출이 0회였어요. 생성 승인이나 renderer까지 오기 전에 차이가 생기고 있었어요.

### 둥근 모서리와 사각형의 차이를 확인했어요

AppKit으로 내용 없는 불투명 시험 창을 만들었어요. 제품에 설치하는 보조 앱이 아니라, 가림 조건을 일정하게 만드는 테스트 도구였어요. 원본 Chrome과 시험 창의 실제 외곽을 모두 확인했어요.

원본 작업 영역은 `(0, 33, 1728, 1084)`였어요. 같은 외곽의 일반 제목 표시줄 창, 그림자 없는 일반 창, borderless 사각형 창을 대조했어요.

| 같은 외곽의 100% 가림 조건             | 관측한 자동 PiP                         |
| -------------------------------------- | --------------------------------------- |
| 일반 제목 표시줄 창, 그림자 있음       | 기본·커스텀 모두 생성되지 않음          |
| 일반 제목 표시줄 창, 그림자 없음       | 커스텀 생성되지 않음                    |
| borderless 사각형 시험 창              | 기본·커스텀 모두 생성됨                 |
| borderless 사각형 시험 창, 그림자 있음 | 가림 기능만 켠 조건에서도 커스텀 생성됨 |

그림자를 없애면 해결된다고 볼 수는 없었어요. 일반 창은 그림자가 없어도 실패했고, 사각형 창은 그림자가 있어도 성공했어요. 성공한 callback의 reason은 `contentoccluded`였고 기존 커스텀 UI가 열렸어요.

원본을 한 픽셀씩 줄이거나 덮는 창을 조금 넓히는 경계 실험도 시도했어요. 하지만 macOS와 Chrome이 위치·크기를 보정해 요청한 정확한 geometry에 도달하지 못한 실행이 있었어요. 그 결과를 ‘1px만 바꾸면 해결된다’는 근거로 사용할 수는 없었어요. 제품이 사용자의 Chrome을 몰래 줄이게 하지도 않았어요.

### Apple 문서에 이미 적혀 있었어요

조사를 이어가며 Apple의 [`NSWindow.OcclusionState.visible` 문서](https://developer.apple.com/documentation/appkit/nswindow/occlusionstate-swift.struct/visible)를 확인했어요.

비직사각형 창은 화면에서 완전히 가려져도, bounding box가 노출 영역에 걸리면 보이는 것으로 간주할 수 있다고 설명하고 있었어요. 완전히 투명한 창도 visible로 남을 수 있다고 했고요.

**사용자가 원본을 볼 수 없다는 사실과 API의 `visible`은 일치하지 않을 수 있었어요.** 제가 구현해야 할 동작의 한가운데에 있는 차이가 이미 공식 문서의 주의사항으로 남아 있었어요.

Chromium에도 오래전부터 [같은 크기 창이 가려진 것으로 판정되지 않는 문제](https://issues.chromium.org/issues/40593221)가 있었어요. 관련 수정 설명은 macOS의 둥근 모서리 때문에 창 경계에 여유가 있어야 가림으로 인정되는 현상을 다루고 있었어요. 같은 외곽의 브라우저 창을 위해 자체 판정을 더한 이력도 있었어요. [관련 Chromium 변경](https://chromium.googlesource.com/chromium/src/+/1a3f08d6cf1b78cc7651dbf8e234977d685ac90e)

설치 버전의 checker를 다시 보니 macOS가 occluded라고 하면 그 판단을 받아들였어요. 추가 계산은 `NSApplication.orderedWindows`, 즉 같은 프로세스의 창 목록을 순회했어요. 외부 앱의 모든 창을 직접 열거해 보완하는 경로는 아니었어요. 같은 Chrome 창끼리의 보완이 외부 일반 앱의 동일 크기 가림까지 해결한다는 뜻은 아니었어요. [Chrome 156의 macOS checker](https://chromium.googlesource.com/chromium/src/+/156.0.8078.74/content/app_shim_remote_cocoa/web_contents_occlusion_checker_mac.mm#514)

일반 창과 사각형 창의 대조 결과는 Apple이 설명한 한계와 맞아떨어졌어요. 다만 이 실험만으로 모서리의 어느 픽셀이 직접 원인인지까지 단정할 수는 없어요.

이 문서를 더 일찍 읽었더라면 어떨까 하는 아쉬움이 남았어요. 창 좌표를 맞추고, 그림자를 바꾸고, callback을 추적하면서 찾아가던 질문의 일부가 이미 설명돼 있었으니까요. 동시에 읽고 지나갈 수 있었던 주의사항이, 실제 실패를 겪고 나니 어떤 의미인지 구체적으로 보였어요.

### 페이지에서 다른 신호를 모으면 알 수 있을까요

남아 있는 신호도 대조했어요. `document.hidden`, `document.hasFocus()`, Intersection Observer v2의 `isVisible`, `requestAnimationFrame`과 영상 프레임 callback 빈도를 관찰했어요.

이번 100% 조건에서는 다른 모니터의 앱을 활성화해 원본이 계속 보이는 상태와, 일반 외부 창이 원본을 완전히 덮은 상태를 안정적으로 구분하지 못했어요. 둘 다 `document.hidden`은 false, 포커스는 false였고, observer의 마지막 결과와 callback 빈도도 구분 근거가 되지 않았어요.

같은 페이지 안에서 불투명 DOM으로 영상을 덮었다가 없애는 대조에서는 IO v2가 `true → false → true`로 바뀌었어요. 계측이 완전히 고장 난 건 아니었어요. 페이지 안에서 감지한 DOM 가림과 외부 앱 창의 가림은 같은 방식으로 판단할 수 없었어요.

시간이나 프레임 수의 작은 차이에 임의의 임계값을 붙이지 않았어요. 이 두 상황을 구분하지 못한 채 PiP를 열면, 다른 모니터의 원본을 불필요하게 따라오는 문제로 돌아가요.

사각형 시험 창에서는 성공했지만, 확장 프로그램에서 다른 앱의 창 장식까지 바꿀 수는 없었어요. **100% Chrome을 같은 크기의 외부 일반 창으로 가렸을 때의 자동 생성은 미해결로 남았어요.**

## 자동으로 못 여는 순간에도, 직접 열 수는 있도록 했어요

작업 영역을 가득 채운 Chrome을 줄이고 싶지 않은 사용자에게도 작은 창을 열 방법은 필요했어요. 자동 callback을 받지 못하는 조건을 확장 프로그램만으로 해결하지 못했다면, 사용자가 원하는 순간 기존 커스텀 PiP를 열 수 있는 전역 단축키를 제공하는 게 현실적인 차선책이라고 생각했어요.

자동 가림 감지가 놓친 상황에서 사용자가 직접 여는 경로예요. 단축키를 누른 만큼 PiP를 열겠다는 의도가 분명해요. 자동 생성의 포커스 보호는 유지하고, 수동 단축키 실행에 한해서 Chrome·PiP로 포커스가 이동할 수 있도록 기준을 달리했어요.

대상 영상도 정했어요. 같은 프로필에서 마지막으로 사용한 지원 영상 창을 골라요. 백그라운드 자동 재생이 방문 순서를 바꾸지는 않아요. 확장 프로그램을 처음 설치해 자체 기록이 없을 때는 Chrome의 `lastAccessed`를 사용해 시작해요.

서로 다른 일반 프로필의 영상을 확장 프로그램이 한데 모아 비교하지는 않아요. 프로필별 확장 프로그램 인스턴스와 키 등록·전달의 경계는 Chrome에 맡겼어요.

같은 키를 다시 누르면 **단축키로 연 창만** 닫아요. 이미 자동 PiP가 있거나 사이트·Chrome에서 직접 연 PiP가 있으면 소유권을 바꾸거나 교체하지 않아요. 수동 창은 원본 탭으로 돌아와도 유지하고, 다음 영상도 같은 세션에서 이어요.

자동 PiP를 꺼두거나 자동 사이트 제외를 적용한 상태에서도 명시적인 수동 명령은 독립적으로 사용할 수 있어요. 사이트 자체의 PiP opt-out과 지원 범위는 계속 지켜요. 수동으로 닫은 뒤 자동화가 즉시 다시 열지 않게 하는 처리도 넣었어요.

### PiP니까 P를 쓰고 싶었어요

기능을 정한 뒤에는 단축키에서 다시 막혔어요. PiP의 P를 쓰면 기억하기 쉬울 것 같았어요. 먼저 생각한 조합은 `Control+Option+Command+P`, 즉 `⌃⌥⌘P`였어요.

설치 Chrome 156의 격리 프로필에 기본값으로 넣어보니 확장 프로그램이 로드되지 않았어요. Chrome의 실제 단축키 설정 화면에서도 같은 조합의 등록이 거절됐어요. 당시 입력기는 Option과 Control 또는 Command를 함께 쓰는 이 조합을 허용하지 않았어요.

대안인 `Control+Command+P`, `⌃⌘P`는 설정 행에 등록됐고 `commands.getAll()`에도 반영됐어요. 하지만 이 조합을 확장 프로그램이 처음부터 전역 기본값으로 지정할 수는 없었어요.

Chrome은 전역 명령의 자동 기본키 제안을 숫자 조합으로 제한해요. macOS에서는 Ctrl의 플랫폼 변환을 고려해 `⌘⇧숫자` 범위를 사용하게 됐어요. 사용자는 Chrome 설정에서 다른 키로 바꿀 수 있어요. 그래서 macOS 기본값은 `⌘⇧9`로 두고, P를 원하는 사용자는 직접 `⌃⌘P`를 지정하도록 했어요. [Commands API의 전역 명령 제약](https://developer.chrome.com/docs/extensions/reference/api/commands#scope)

| 조합   | Chrome 156에서 확인한 범위                        |
| ------ | ------------------------------------------------- |
| `⌃⌥⌘P` | manifest 로드·설정 화면 등록 모두 거절            |
| `⌃⌘P`  | 사용자 지정 등록·API 반영 확인                    |
| `⌘⇧9`  | 제품 기본값, 실제 macOS 전역 입력과 PiP 생성 검증 |

`⌃⌘P`는 등록할 수 있었지만, 외부 앱에서의 실제 실행은 추가 확인이 필요해요. Windows·Linux의 기본키는 `Ctrl+Shift+9`로 선언했고, 실제 전역 키 입력과 PiP 생성은 macOS의 기본키 `⌘⇧9`로 확인했어요.

### 설정 위치를 찾아다니지 않도록 했어요

Commands API에는 확장 프로그램이 사용자의 binding을 직접 바꾸는 setter가 없었어요. 팝업 안에 저장 버튼을 만들어 놓고 실제 Chrome 단축키를 바꾼 것처럼 보이게 할 수는 없었어요.

팝업에 현재 등록된 키를 표시하고, **단축키 설정** 버튼으로 `chrome://extensions/shortcuts`를 열도록 했어요. 값은 기본 문자열을 고정해서 보여주지 않고 `commands.getAll()`에서 다시 읽었어요. 지정되지 않았다면 ‘미지정’으로 안내했어요.

P를 쓰려면 팝업에서 단축키 설정으로 이동하고, `⌃⌘P`를 입력한 뒤 전역 실행을 선택하면 돼요. 키를 바꾼 뒤 팝업을 다시 열면 등록된 값을 읽어요.

Chrome 내부 설정에 기대는 기능이라도 사용자가 찾아야 하는 위치와 선택할 실행 범위까지 연결해주고 싶었어요. 공개 API로 전역 scope를 조회할 수는 없어, 키가 표시된다는 사실만으로 외부 앱 실행까지 보장하는 UI는 만들지 않았어요.

### 만들자마자 포커스를 돌리면 안 될까요

수동 실행에서 PiP로 포커스가 이동하는 건 허용했어요. 그래도 생성 직후 원래 앱으로 바로 돌려줄 수 있다면 더 편할 것 같았어요.

PiP의 focus 이벤트를 받자마자 한 번만 `chrome.windows.update(pipWindowId, { focused: false })`를 호출해봤어요. 인위적인 대기나 포커스 반복문은 넣지 않았어요.

세 번 모두 API는 정상 응답했지만 PiP와 Chrome은 활성 상태를 유지했고, 원래 외부 앱으로 돌아가지 않았어요. 빠른 응답을 포커스 복원 성공으로 해석할 수 없었어요.

Chrome의 창 API는 이전 외부 앱의 식별자를 알려주거나 그 앱을 지정해 활성화하는 계약이 아니에요. 창을 만든 직후 더 빨리 호출하는 것만으로 해결할 근거도 얻지 못했어요. 이 시도는 제품 코드에 넣지 않았어요. [Chrome 창 API](https://developer.chrome.com/docs/extensions/reference/api/windows)

팝업에는 수동 실행 시 PiP로 포커스가 이동한다는 점을 함께 안내했어요. 이 경로에서도 잠깐 debugger를 사용하므로 Chrome의 디버깅 안내가 나타날 수 있어요.

## 작은 확장 프로그램에도, 상태를 전달하는 주소가 필요했어요

이 과정에서는 화면에 보이지 않는 기반도 계속 고쳤어요. 런타임과 테스트를 TypeScript로 옮기고, content script·background·popup 사이의 통신에 `webext-bridge`를 적용했어요.

타입을 붙인 것만으로 비동기 메시지의 의미가 고정되지는 않았어요. 같은 tab과 frame이라도 이미 다른 문서로 이동했을 수 있고, 이전 영상의 응답이 새 PiP에 도착할 수 있었어요.

탭·프레임·영상 token·이탈 주기·소유 session을 함께 확인했어요. 이전 세션의 닫힘이 다음 창의 소유권을 지우거나, 오래된 취소가 새 요청을 막지 않도록 했어요. 설정 저장도 payload뿐 아니라 발신 context를 확인했어요.

라이브러리의 실제 동작도 살펴야 했어요. 사용한 bridge 버전은 최상위 frame ID를 생략할 수 있어 0으로 정규화했어요. 응답 라우팅 중 sender 객체가 바뀌므로, 비동기 큐에 넣기 전에 필요한 식별자와 payload를 복사했어요. 재주입 때는 import 부작용까지 포함해 중복 controller와 포트를 만들지 않도록 했어요.

응답을 받지 못하는 대상이 전체 PiP 큐를 계속 붙잡지 않게 1.5초 대기 제한도 뒀어요. 이 제한은 제가 기다리는 시간을 끝내는 것이에요. 이미 전달되거나 보류된 메시지를 취소하는 기능은 아니어서, 늦게 도착한 요청의 token·주기를 끝에서 다시 확인해야 했어요.

`webextension-polyfill`로 공통 API를 Promise 기반으로 정리했지만 자동 PiP와 CDP 경로는 Chrome 전용이에요. `web-ext`의 호환성 진단에서는 Chrome 전용 API 때문에 발생하는 차이만 따로 분류해, 그 밖의 오류를 놓치지 않도록 했어요.

## 검증 도구가 ‘보이는 상태’를 바꾸기도 했어요

이번 프로젝트에서 가장 조심스러웠던 건, 관찰하려고 붙인 도구가 포커스와 가시성을 바꿀 수 있다는 점이었어요.

Playwright의 focus emulation을 켜면 실제 비활성 탭이 보이는 것처럼 남을 수 있었어요. 테스트를 통과시키려고 이 상태를 이용할 수는 없었어요. `connectOverCDP({ noDefaults: true })`를 사용하고 focus emulation을 끈 뒤, 원본은 실제 visible·focused이고 다른 탭은 hidden인지 확인했어요.

탭이 active이고 `windows.update`가 성공했다는 사실만으로 시작하지도 않았어요. macOS의 테스트 프로세스가 실제 active인지, 숨김 상태가 아닌지, 대상 창과 문서가 포커스를 갖는지까지 기다렸어요. 활성화 요청을 수락했지만 아직 앱이 active가 아닌 표본도 있었어요.

커스텀 PiP 크기가 이상하게 나왔던 실행에서는 테스트 시작의 `--window-size` 옵션이 새 PiP 요청 크기까지 덮고 있었어요. 그 옵션을 없애고 처음의 일반 창만 따로 조절했어요. worker 재시작도 CDP target이나 클라이언트 객체가 바뀌었다는 것만으로 판정하지 않고, 새로운 JavaScript 전역 상태를 확인했어요.

Chrome을 여러 개 실행하면 같은 앱 식별자를 사용해 `Cmd+Tab`이 엉뚱한 Chrome 프로세스로 돌아가기도 했어요. 자동화에서는 정확한 테스트 PID를 지정해 활성 상태를 확인하고, 실제 `Cmd+Tab` 동작은 직접 사용하면서 확인했어요.

## 가져오고 싶었던 건, 신경 쓰지 않아도 이어지는 경험이었어요

현재 Auto PiP는 Chrome의 자동 callback을 우선하고, 지원되는 Chrome 내부 탭 전환에서는 debugger 경로로 보완해요. 원본이 다른 모니터에 보이면 앱 포커스가 사라졌다는 이유만으로 새 창을 열지 않아요. 자동으로 연 창과 사용자가 직접 연 창의 수명도 구분해요.

Chrome 창을 최소화할 때 새 자동 PiP를 띄우지는 않아요. 최소화 상태에서 새 PiP가 필요하면 직접 열어요. 다른 앱으로 이동할 때의 자동 생성은 Chrome의 가림 기능과 재생 자격을 따르며, 동일 크기의 일반 외부 창으로 덮인 상황은 여전히 놓칠 수 있어요.

일반 영상은 원본과 오디오를 원래 탭에 남기고, Netflix와 쿠팡플레이에서는 같은 요소를 옮겨 공통 UI를 사용해요. 다른 사이트나 iframe의 보호 영상은 기본 영상 PiP로 보완할 수 있고, 이때 커스텀 탐색·휠·크기 보정은 적용되지 않아요. 사이트별 플레이어 구조와 보호 정책에 따라 지원 범위가 달라져요. 아직 스토어 공개 전 단계예요.

한계를 하나씩 만날 때마다 다음에 풀어야 할 질문도 달라졌어요.

PiP를 열 수 있으면 될 줄 알았는데, 어떤 영상을 언제 교체할지부터 정해야 했어요. 같은 창이 나와도 읽던 입력과 다음 단축키까지 이어져야 했어요. 종료 이벤트 뒤에 다음 영상이 기다리고 있었고, 브라우저가 보인다고 하는 창이 제 눈에는 보이지 않았어요.

오랜만에 정말 재미있었고, 문제에 깊이 몰입했던 프로젝트였어요. 탭 아이콘의 점선 하나를 떠올린 데서 Chromium의 observer와 macOS 창 판정까지 내려갔어요. 찾던 경로를 연결한 뒤에도 둥근 모서리라는 작은 경계가 남았고요.

‘자동’이라는 말에 필요한 건 실행 조건만이 아니었어요. 기다려야 하는 순간, 사용자의 직접 조작에 자리를 내줘야 하는 순간, 감지하지 못한 상황을 인정하고 수동 실행을 제공하는 순간도 함께 있었어요.

Arc에서 익숙했던 작은 창을 가져오며, 저는 창 바깥의 경험을 더 오래 들여다보게 됐어요.
