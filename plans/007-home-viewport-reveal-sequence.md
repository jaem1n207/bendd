## Problem

최상단에서 초기 연출이 진행되는 동안 Writing으로 스크롤하면, Writing의 본문은 지연 0ms·280ms·blur 0으로 등장한다. 앞부분의 900ms 선명화와 목록 순서가 이어지지 않아 바로 표시되는 것처럼 느껴진다.

006은 이미 시작한 효과를 스크롤 때문에 취소하지 않도록 고쳤다. 그러나 처음 화면 밖에 있던 요소는 초기 시간표의 대상이 아니며, IntersectionObserver의 별도 빠른 경로로 들어간다. 따라서 이 문제는 남아 있던 140ms 취소 코드가 아니라 **최초 뷰포트와 이후 최초 진입의 모션 정책 차이**다.

사용자는 확인 질문에서 “보이는 시점부터 순차 등장”을 선택했다. 이 계획은 처음 화면 밖이었던 요소의 280ms/200ms 무지연 정책을 대체한다. 처음 로드의 연출이 끝난 뒤 내려가도 아직 보지 않은 요소에는 같은 정책을 적용한다. 이미 표시했거나 시작한 요소는 다시 재생하지 않는다.

## Target

### 공통 재생 조건

초기 로드와 스크롤에 의한 최초 표시 모두 같은 시간표와 효과를 사용한다.

- 시작 전: `opacity: 0`, 대상별 blur와 Y 이동. 종료: `opacity: 1`, `blur(0px)`, `translateY(0px)`.
- 각 요소의 재생: **900ms**, **`cubic-bezier(0.25, 0.1, 0.25, 1)`**, `fill: 'both'`.
- 첫 뷰포트의 기존 예약과 재생은 유지한다. 새로 진입한 요소의 시간은 해당 최초 진입을 기준으로 잡는다. 페이지 로드 시각을 빼서 이미 진행된 opacity로 시작하지 않는다.
- 시작한 요소는 화면 밖으로 나가도 자연 종료한다. 위아래로 스크롤하거나 observer가 다시 통지해도 새 효과를 만들지 않는다.
- 첫 화면 연출이 종료된 뒤에도 아직 `pending`인 요소는 이 900ms 정책을 사용한다. “초기 연출 중인지”에 따라 280ms 경로로 갈라지는 시간 경계를 추가하지 않는다.

### Writing 예시와 기존 간격

Writing 제목·글 3개·손글씨가 함께 처음 보이는 경우, 이 묶음의 시작을 `T`로 둔다.

| 요소                        |      시작 |        종료 |
| --------------------------- | --------: | ----------: |
| 제목                        |         T |   T + 900ms |
| 첫 글 또는 선택된 보이는 글 |  T + 36ms |   T + 936ms |
| 두 번째 글                  |  T + 96ms |   T + 996ms |
| 세 번째 글                  | T + 156ms | T + 1,056ms |
| 손글씨                      | T + 216ms | T + 1,116ms |

손글씨의 정상 등장 후 360ms 단일 회전은 기존대로 이어진다. 추가 글은 기존대로 제목 +216ms부터 같은 시작 시점을 공유하고, 메모는 실제 마지막 본문 예약 +60ms다. 새로운 DOM 선택 상태를 만들지 않는다.

- stack은 36ms 간격, 목록 첫 글은 제목 +36ms, 나머지 글은 60ms 간격이다.
- 여러 섹션이 같은 관측에서 함께 들어오면 DOM 그룹 순서와 마지막 예약 시작 +120ms의 섹션 간격을 유지한다.
- 새 관측이 앞서 예약한 미래 시점과 겹치면 그 예약 뒤에 연결한다. 같은 list의 후속 글은 마지막 본문 예약 +60ms, heading 다음 첫 글은 +36ms, 같은 stack 후속 본문은 +36ms, 다른 그룹은 마지막 예약 +120ms를 기준으로 한다. 그 시각이 이미 지났으면 현재 관측 시각에서 시작한다.
- **이미 만들어진 Animation의 delay나 currentTime은 수정하지 않는다.** 새로 보이는 대상의 예약만 계산한다. 모든 초기 효과가 완료될 때까지 기다리게 하지 않는다.
- 새 묶음의 상대 시간표에도 기존 600ms 상한과 손글씨 60ms 간격 보존 규칙을 재사용한다. 이 상한은 새 묶음의 시작 기준이며 문서 로드 후 600ms가 지났다는 이유로 지연을 없애지 않는다.

### 부분 진입과 observer 순서

1. `entries` 배열 순서가 아니라 기존 `elements`의 DOM 순서와 `data-reveal-group`/`data-reveal-sequence`를 사용한다. 노트가 DOM에서 글보다 앞서 있어도 시간표상 뒤로 보낸다.
2. 이번에 실제로 교차한 `pending` 대상들만 예약한다. 화면 밖의 나머지 항목 전체에 Animation을 만들지 않는다. 일부만 보인 섹션은 보이는 대상으로 시작하고, 뒤늦게 보이는 본문은 위 간격으로 연결한다.
3. 같은 항목의 중복 통지와 두 번의 빠른 observer callback에서도 한 번만 예약한다. 기존 `active`/`visible` 대상은 새 목록에서 제외한다.
4. 손글씨는 예약할 때 이미 예약했거나 이번 관측에 포함된 같은 그룹의 마지막 본문 시작 +60ms를 따른다. 아직 화면 밖인 본문을 기다리는 대기열을 만들지 않는다. 나중에 더 많은 본문이 들어와도 이미 시작한 메모를 숨기거나 다시 재생하지 않는다.
5. Writing 위치로 복원되어 초기화되면 현재 뷰포트를 기존 초기 시간표로 처리한다. `scrollY > 0` 자체는 생략 조건이 아니다.

### 선명화·성능·예외

| 대상                 | 데스크톱 blur | 폭 640px 이하 blur | Y 이동 |
| -------------------- | ------------: | -----------------: | -----: |
| 일반 텍스트·제목     |          10px |                6px |    8px |
| Writing 글           |           8px |                4px |    6px |
| Craft 카드           |           6px |                3px |    6px |
| 손글씨               |           4px |                2px |    0px |
| 큰 Projects 미리보기 |           0px |                0px |    4px |

- 초기와 새 진입을 합쳐 **예약/실행 중 blur 단위 최대 12개**를 유지한다. 새 묶음마다 별도의 12개를 허용하지 않는다. 예약 여유가 부족한 항목은 같은 순서·900ms로 opacity/transform만 적용한다. 성능 때문에 모든 대상의 delay를 0으로 바꾸지 않는다.
- `createHomeRevealPlan`의 기존 주요 텍스트·첫 항목 우선 배분을 재사용한다. 필요하면 사용 가능한 blur 개수를 인자로 전달하고, 완료·취소·cleanup에서 예약을 반환한다. 매 프레임 React 상태나 레이아웃 측정은 추가하지 않는다.
- reduced motion, Tab/포커스/실제 컨트롤 활성화, 실제 테마 변경, 페이지 이탈, 내비게이션 복귀 및 JavaScript/CSS 복구 경로를 유지한다. 이미 읽히는 콘텐츠를 다시 숨기지 않는다.
- 완료 후 기존 `show()`/cancel로 filter·transform을 해제한다. 노트 회전의 화면 밖 생략·좁은 화면 절반 각도·정리 정책도 유지한다.

**값의 근거:** 900ms와 초기 곡선은 사용자가 선택한 홈의 선명화 연출이다. 36/60/120ms와 손글씨 60ms는 기존 명세 값이다. 감사 규칙의 마케팅 긴 연출 예외를 적용하며, 일반 컨트롤의 짧은 duration으로 교체하지 않는다.

## Steps

1. 회귀 fixture에 실제 형태의 Profile과 화면 밖 Writing(list 제목·3글·손글씨)을 만든다. 초기 900ms가 진행 중인 시각에 Writing을 교차시키고, Writing도 900ms·초기 곡선·blur·36/60ms 순서로 시작해야 한다는 실패를 먼저 확인한다. Profile의 Animation이 재생성·취소되지 않는지도 확인한다.
2. 시간표 입력을 최초 뷰포트뿐 아니라 새 진입 묶음에도 재사용하도록 정리한다. DOM 순서, 선행 항목, 손글씨 후행, 600ms 상한, 사용 가능한 blur 예산의 순수 로직을 테스트한다.
3. observer의 280ms/200ms·본문 delay 0·blur 0 경로를 공통 계획/재생 경로로 교체한다. 이미 예약한 시작 시점과 새 묶음의 연결 기준만 저장하고, scroll 이벤트로 전체 시간표를 다시 계산하지 않는다.
4. 초기와 진입에 걸친 blur 예산과 자연 종료·즉시 표시·cleanup 정리를 연결한다. pending 대상에 프레임 루프나 상시 레이어를 만들지 않는다.
5. 늦은 진입, 쪼개진 observer callback, 빠른 재진입, 손글씨, 접근성 예외를 검증한다. 기존 “화면 밖이면 280ms·무지연” 테스트 기대를 새 명세로 바꾼다. 테스트 삭제로 통과시키지 않는다.
6. 실제 동작을 검증한 뒤 홈 명세의 초기 범위·화면 밖 진입·입력 표를 갱신한다. 기존 47개 통과 기록은 이전 코드의 결과로 남기고 새 증거를 별도로 기록한다.

## Notes

이번 감사는 사용자가 지적한 Writing 최초 진입 경로를 집중 검토했다. 코드와 테스트에서 원인을 확인했으며, 이번 단계에서는 소스·테스트·명세를 수정하거나 브라우저 재현·테스트·빌드를 실행하지 않았다. 체감과 성능의 최종 판정은 구현 후 위 재현 조건으로 한다.

006의 “진행 중 효과 유지”는 보존한다. 007은 006에서 범위 밖으로 남았던 새 뷰포트 요소의 최초 등장까지 사용자 의도에 맞추는 후속 계획이다.

## 실행 기록 — 2026-09-30

- 최초 뷰포트와 IntersectionObserver 진입에 같은 `reveal()`/`createHomeRevealPlan`을 사용했다. 새 진입의 280ms/200ms 분기와 강한 entry 곡선을 제거하고 900ms·기존 초기 곡선을 적용했다. 시작한 Animation 인스턴스의 delay/currentTime은 변경하지 않는다.
- DOM 순서로 새 대상을 정렬하고, 그룹별 마지막 본문 예약·종류·진입 항목 수를 기록한다. 쪼개진 교차 통지에도 36/60ms 간격을 연결하고, 네 번째 목록 시작 이후 지연을 계속 늘리지 않는다.
- 초기와 이후 진입이 공유하는 blur 예약 12개 상한을 적용했다. 남은 예산을 순수 시간표 함수에 전달하고 finish/cancel/cleanup에서 반환한다. 손글씨 +60ms·360ms 단일 회전과 즉시 접근성 경로를 보존했다.
- 회귀 테스트에서 먼저 **10개 실패**를 확인했다. 최종 홈 테스트 **54개**, 프로덕션 빌드 통과. 홈 First Load JS는 108kB다. 테스트/빌드의 기존 경고는 별도 기존 항목으로 남겼다.
- 실제 1280×720 브라우저에서 첫 효과 시작 약 91ms 후 Writing 제목·글 3개·메모가 보이도록 스크롤했다. 수정 전의 동시 280ms를 확인했고, 수정 후에는 제목 기준 0/36/96/156/216ms 시작과 각 900ms를 확인했다. 이미 시작한 효과의 조기 취소와 opacity 역행은 없었다.
- 정상·25% 속도, 390×844의 초기 연출 종료 후 Writing 첫 진입을 관측했다. 총 blur 최대 12개, 자연 종료 후 효과 해제도 확인했다. 성능의 긴 프레임 관측과 재확인 기록은 [최신 홈 모션 명세](../docs/design-docs/home-initial-motion-brief.md)에 남겼다.
- 실제 기기·OS 설정·네이티브 스크롤바·높은 배율·다른 브라우저 검증은 수행하지 않았다. 분할 통지·빠른 중복 진입·접근성 예외는 단위 테스트로 보호했다. 체크리스트 전체를 실기기로 수행한 것으로 간주하지 않는다.
- 변경 소스는 `home-motion.tsx`, 해당 테스트, `home-reveal-plan.ts`, 해당 테스트다. 홈 명세와 계획 기록을 갱신했으며 Dock·CSS·HomeStudio 및 무관한 미커밋 작업은 보존했다. 커밋·push·배포는 수행하지 않았다.
