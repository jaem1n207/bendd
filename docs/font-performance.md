# 웹폰트 로딩 시간 비교

## 결과

동일 기기·네트워크 조건에서 원본과 최종 수정본을 번갈아 측정했다. 각 페이지·방문 유형·버전당 5회, 최종 60회다. 아래 숫자는 중앙값이며 원자료에는 모든 측정값과 min/max, 같은 회차의 차이를 남겼다. 단일 기기의 제한된 표본이므로 실서비스 전체의 속도 보장으로 해석하지 않는다.

| ------- | ------- | -----------: | ------------: | -------------------------: | --------------: |
| 홈      | 첫 방문 |    508 → 420 | 1,988 → 1,968 |                  837 → 551 |           6 → 6 |
| 홈      | 재방문  |    248 → 228 | 1,664 → 1,668 |                  579 → 528 |           6 → 6 |
| 본문    | 첫 방문 |    380 → 384 |     380 → 384 |              3,042 → 2,529 |           8 → 5 |
| 본문    | 재방문  |    296 → 304 |     296 → 304 |                  708 → 668 |           8 → 5 |
| Shuffle | 첫 방문 |    264 → 248 |     264 → 248 |              2,640 → 2,059 |           6 → 2 |
| Shuffle | 재방문  |    188 → 188 |     188 → 188 |                  431 → 420 |           6 → 2 |

첫 방문 폰트 준비는 세 페이지 모두 5쌍 전부 빨라졌다. 중앙값 차이는 홈 −287ms, 본문 −513ms, Shuffle −581ms다. 재방문은 폰트의 실제 네트워크 전송이 양쪽 모두 0 B이며 큰 속도 이득으로 주장하지 않는다.

본문 FCP/LCP 중앙값은 첫 방문 +4ms, 재방문 +8ms의 작은 증가가 남았다. 같은 회차의 FCP 차이는 첫 방문 −4~+12ms, 재방문 −20~+16ms로 변동 범위가 겹친다. 이 결과로 전체 페이지가 모든 지표에서 빨라졌다고 주장하지 않는다. Shuffle 재방문 FCP는 이전 단계의 184→212ms 지연에서 최종 188→188ms로 복구됐다.

## 전송과 요청

요청 수는 캐시 조회도 포함한다. 재방문 폰트가 실제로 네트워크에 전송됐는지는 cachedFontRequests와 fontTransferBytes로 따로 확인했다. CDP 전송 바이트는 response body와 HTTP 비용을 포함하므로 기존 body-only 표와 다르다. 전체 페이지 요청/전송은 관찰 구간의 동일 origin 리소스 기준이다.

## 관측한 회귀와 수정

1. Next.js의 홈 prefetch가 본문에서도 Home/notes/serif/dots를 preload했다. 기존 브라우저 검사 2개에 금지 조건을 추가해 실패를 확인한 뒤, pathname을 아는 공통 FontPreloads로 이동했다. 홈 장식 preload는 홈에서만 출력된다.
2. Home/notes/serif를 분할하면 현재 홈에서는 항상 두 파일을 함께 받는다. 1차 5회에서 홈 재방문 폰트 준비 중앙값이 621→704ms로 증가했다. 원본 6개 요청 예산 검사도 9개로 실패했다. 세 역할을 각각 한 파일로 통합해 6개로 복구하고, 홈 body-only 폰트 전송량을 198,240→158,636 B로 줄였다. ASCII 전용 화면에서 이 역할을 재사용할 경우의 비용은 font-optimization.md에 기록했다.
3. 통합 후에도 보통 우선순위의 core preload에서 Shuffle 첫 방문 FCP가 5쌍 모두 32–92ms 지연됐다. 중앙값은 260→316ms였다. 우선순위와 사용 범위를 제한하는 진단 후, 비홈에서는 추가 preload 자체를 제거해 원래의 CSS 발견 경로를 유지했다. 홈은 필요한 6개만 preload한다. 이 구성으로 위 최종 60회를 다시 측정했다.

4. 비홈에서 빈 출력을 내던 RootLayout의 폰트 Client Component도 초기화에 참여했다. 이 상태의 Shuffle 재방문 FCP 중앙값은 184→212ms, 쌍별 중앙값 +28ms였다. preload 컴포넌트를 HomeStudio에만 배치해 불필요한 비홈 초기화를 제거하고 위 최종 표를 얻었다.

font-display와 fallback family/metric/순서는 변경하지 않았다. Home/notes/serif 단일 파일과 비홈 core preload 생략은 원래 요구에서 벗어난 조정이다. 비홈은 CSS 발견 이후 다운로드를 시작하므로, core를 무조건 일찍 받는 장점은 포기했다. 폰트 표시 정책과 fallback은 보존했다. 최종 폰트와 CSS에서 화면 22개 / 183,348,000픽셀의 변경 0개, 홈·MDX 브라우저 15개와 다운로드 probe 16개를 확인했다.

## 측정 조건과 해석

- 원본: main 545b5b5의 동일 콘텐츠 production 빌드. 후보: 이 PR의 최종 폰트·preload 수정. 두 서버는 localhost:3140/3141, 실제 시계 사용.
- 환경: {"platform": "darwin", "release": "27.0.0", "cpu": "Apple M1 Pro", "measuredAt": "2026-11-03T23:51:07.379Z"}. Chromium 151.0.7922.34.
- 1440×900, DPR1, ko-KR, Asia/Seoul, light, 기본 모션 설정(no-preference). 랜덤 seed 42. 영상·애니메이션을 정상 실행하며 픽셀 비교용 Clock/마스킹을 사용하지 않는다.
- CDP: download 10 Mbps / upload 1 Mbps / latency 40ms / CPU 4배 감속. localhost production의 통제 실험이며 실제 CDN·HTTP/2·모바일 실기기 측정은 아니다.
- 각 회차의 before/after 실행 순서를 번갈아 바꾼다. 첫 방문은 새 browser context, 재방문은 같은 context에서 새 페이지로 정상 탐색한다. 강력 새로고침/BFCache가 아니다. App Router 내부 client navigation은 별도 측정하지 않았다. 비홈의 자동 홈 폰트 preload를 제거했으므로, 이후 홈으로 이동할 때 필요한 폰트는 그 시점에 요청될 수 있다. OS 디스크·폰트 캐시는 초기화하지 않았다.
- Playwright route는 HTTP 캐시를 끄므로 사용하지 않는다. service worker는 차단한다. 외부 DNS 요청은 막고 visitor-location만 CDP Fetch로 동일 응답을 준다. 외부 서비스 지연을 제외한 첫 페이지 리소스 비교다.
- LCP는 PerformanceObserver의 마지막 entry, FCP는 PerformancePaintTiming이다. 최소 7초를 관찰하고, 폰트 처리가 늦으면 완료와 다음 두 프레임까지 추가 대기한다(대기 상한 30초).
- 폰트 시간은 DOMContentLoaded 이후 document.fonts.ready와 두 requestAnimationFrame을 지난 시점이다. 다운로드·등록·레이아웃 완료 후 표시 가능한 시점의 대리 지표이며, 개별 글자의 실제 pixel paint 시각을 직접 측정한 값은 아니다. fontLoadEnd와 fontResources.responseEnd도 원자료에 있다.
- 원본과 후보 모두에서 폰트 응답 종료 후 준비까지 긴 지연이 발생한 샘플이 있다. 환경 스케줄링과 폰트 처리의 원인을 분리하지 못했으므로 이상치를 제거하지 않고 범위를 함께 공개한다. 평균적인 개선과 최악값 개선을 혼동하지 않는다.
- 홈 LCP는 기존 등장 모션에 따라 크게 변한다. LCP/FCP와 폰트 준비를 구분하고 모든 지표가 확실히 개선됐다고 주장하지 않는다.
- Shuffle 페이지에서는 로딩 관찰 후 실제 버튼을 눌러 애니메이션 완료와 폰트 loaded 상태도 확인했다. 실행 시간은 사용자 입력·애니메이션 설정을 포함하며 페이지 LCP/FCP와 분리된다.

## 재실행

두 checkout을 같은 Node/pnpm 버전으로 각각 production build/start한 뒤 실행한다. 폰트 생성은 수동이며 이 측정기도 build/dev에 연결하지 않는다. 다른 검사나 빌드를 동시에 실행하지 않는다.

```sh
FONT_BENCH_BASELINE_ROOT=/path/to/before FONT_AUDIT_PLAYWRIGHT=/path/to/recent/playwright node scripts/benchmark-fonts.mjs output/playwright/font-optimization/timing
```

기본은 3페이지·5회다. FONT_BENCH_ROUNDS와 FONT_BENCH_ROUTE로 진단 범위를 바꿀 수 있다. 기본적으로 설치된 @playwright/test를 사용하며, 해당 Chromium 실행 파일이 설치되어 있어야 한다. 완료된 cold/warm 쌍은 재실행 시 재사용하므로 완전히 새 측정에는 새 출력 경로를 사용한다.

[최종 원자료](font-optimization/timing-final-samples.json) · [최종 요약](font-optimization/timing-final-summary.json) · [홈 분할 단계](font-optimization/timing-split-home-summary.json) · [보통 우선순위 단계](font-optimization/timing-normal-priority-summary.json)

재방문 Shuffle FCP의 쌍별 중앙값 차이 20ms 이내라는 진단 기준은 수정 전 +28ms로 실패했고 최종 +4ms로 통과했다. 이 기준은 수동 진단용이며 CI에 시간 기반의 불안정한 검사를 추가하지 않았다.

단계별 재방문 초기화 원자료: [RootLayout 경계 단계](font-optimization/timing-root-boundary-summary.json). 최종 빌드 ID는 최종 원자료의 buildIds에 있다.

CLS는 홈 0→0, 본문 첫 방문 0.00457→0.00065, 본문 재방문 0.00037→0.00037, Shuffle 첫 방문 0.00013→0.00013, Shuffle 재방문 0→0이다. 모두 작은 값이며 큰 체감 개선으로 해석하지 않는다.
